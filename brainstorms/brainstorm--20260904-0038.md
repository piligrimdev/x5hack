## Все идеи — финальный список

1. Redis как Celery broker вместо RabbitMQ — один сервис, два назначения (broker + cache)
2. Idempotency key (receipt_id) на POST /purchases → 201 или 409 + retry на стороне кассы
3. Outbox-паттерн без брокера: `purchase_events` таблица → Celery worker сканирует pending записи
4. Materialized view / precalculated поле в Postgres для рейтинга — не пересчитывать на каждый запрос
5. LLM-вызов всегда через Celery (async) → API отвечает 202 сразу, клиент пуллит результат
6. Аватар = JSON-параметры в Postgres (level, skin, accessory_ids), рендер на клиенте — без файлового хранилища
7. Мобилка: stale-while-revalidate — сначала кэш, затем фоновый refresh
8. TTL-стратегия: аватар — до следующей покупки; челлендж — до конца дня; рейтинг — 30–60 мин
9. Celery Beat: одна ночная джоба `generate_challenges_nightly`, остальное — event-driven через .delay()
10. Fallback при ошибке LLM: шаблонный челлендж из Postgres, а не пустой экран
11. Сегмент юзера — enum-поле в таблице users, пересчитывается Celery раз в сутки
12. Купоны = записи в Postgres с expires_at и used_at, пачка генерируется Celery заранее
13. Эмуляция DLQ через таблицу failed_tasks в Postgres + Celery Beat retry джоб
14. Две очереди Celery: high_priority (update_economy, update_rating) + low_priority (generate_challenges, segmentation)
15. Поле reasoning в /challenges/current — объяснение почему этот челлендж (UX + hit rate для жюри)
16. HEAD-запрос или /me/version endpoint — мобилка проверяет изменения без full pull
17. RabbitMQ исключается — нет сценария где его фичи критичны для этих 4 задач на хакатоне

## Final Summary

### Ключевые темы
- Упрощение инфраструктуры: Redis заменяет RabbitMQ, монолит вместо микросервисов
- Надёжность через идемпотентность: receipt_id + 409, outbox-паттерн без брокера
- Async-first для LLM: все тяжёлые вызовы через Celery, API не блокируется
- Клиентский кэш вместо push: мобилка сама управляет свежестью данных
- Объяснимость ИИ встроена в архитектуру (reasoning field)
