# Spec-Driven Feature

Превращай согласованный продуктовый замысел в прослеживаемую спецификацию и проверяемый результат. Спецификация описывает ожидаемое поведение; реальное состояние кода и проверок подтверждай отдельно.

## Граница применения

- Начинай после того, как определены пользователь, проблема, ценность и границы гипотезы, либо когда пользователь прямо просит специфицировать конкретную фичу.
- Для product discovery сначала используй профильную методику. Не выбирай сегмент, ценность или концепцию за пользователя ради заполнения spec.
- Режим **spec-only** заканчивается согласованной спецификацией и планом проверки. Код не создавай, если реализация не поручена.
- Режим **delivery** включает реализацию и convergence. Запрос «сделай/реализуй фичу» разрешает пройти весь необходимый цикл.
- Для многоэтапной разработки используй доступный GSD как оркестрацию состояния, планов и проверок. Этот скилл задаёт качество спецификации и сопоставление требований с результатом; не создавай второй конкурирующий журнал.

## Перед началом

1. Прочитай применимые `AGENTS.md`, состояние проекта, существующие требования и ближайшие аналоги в кодовой базе.
2. Зафиксируй цель, границы, входные данные и наблюдаемые критерии готовности. Не переноси автоматически стек, архитектуру или практики из учебного шаблона.
3. Выбери масштаб: короткая spec для обратимой локальной правки; полный цикл для новой сквозной функции, AI-модуля, API/данных или высокого риска.
4. Если используется внешний CLI или шаблон, сначала проверь актуальную официальную документацию. Не устанавливай GitHub Spec Kit, OpenSpec и расширения только потому, что они упомянуты в методическом материале.

## Семь стадий

### 1. Constitution и контекст

Собери только релевантные правила: архитектурные границы, интерфейсы, качество, безопасность, данные, совместимость и обязательные проверки. Предпочитай уже принятые правила проекта. Clean Architecture, TDD, Database First, REST/WebSocket и конкретные версии языков являются вариантами, пока проект или пользователь не закрепили их.

### 2. Specify

Опиши поведение по [шаблону спецификации](references/spec-template.md). Требования должны быть однозначными, проверяемыми и иметь стабильные ID. Добавляй API, схему данных и файловую структуру только когда они относятся к функции. Для AI-функции обязательно зафиксируй контракт качества, fallback и оценивание.

### 3. Clarify

Найди противоречия, пропуски, неявные состояния, ошибки, пограничные случаи и решения, влияющие на пользователя, стоимость, срок или совместимость. Рутинные обратимые детали решай по правилам проекта. Содержательный выбор продукта оставляй пользователю и задавай один конкретный вопрос после выполнения независимой части.

### 4. Plan

Составь план изменений по компонентам и зависимостям. Для каждого шага укажи связанные требования, изменяемые артефакты, способ проверки и риск. Сверь план с реальной архитектурой до реализации.

### 5. Tasks

Разбей план на атомарные, проверяемые задачи с ясным результатом. Каждая задача ссылается на требования и критерии приёмки. Ориентиры «10–20 задач» и «до 15 минут» из воркшопа используй как эвристику, а не обязательное правило. При параллельной работе разделяй владение файлами и зависимостями.

### 6. Implement

В режиме delivery выполняй задачи последовательно по зависимостям. После каждого содержательного изменения запускай минимально достаточные проверки. Обновляй спецификацию, если пользовательское поведение согласованно изменилось; не переписывай её задним числом, чтобы скрыть отклонение.

### 7. Converge

Сопоставь спецификацию, план, задачи, реализацию и фактические проверки по [чек-листу](references/convergence-checklist.md). Исправь несоответствия либо явно зафиксируй согласованное решение и остаточную работу. Завершай только когда обязательные критерии подтверждены наблюдаемыми доказательствами.

## Контрольные точки

- Пользователь подтверждает продуктовые решения и существенные изменения контракта; агент самостоятельно делает рутинную подготовку и проверку.
- До кода проверь, что план покрывает требования и не опирается на неизвестные интерфейсы или данные.
- Критические части реализации требуют человечески читаемого объяснения и проверки, соразмерной риску.
- Сохраняй трассировку `решение → требование → задача → изменение → проверка`.

## Результат

В spec-only режиме передай спецификацию, открытые продуктовые решения, план проверки и границы сделанных допущений. В delivery режиме дополнительно передай реализацию, фактические проверки, отклонения и остаточные риски. Команды установки, создание issue/PR, commit, публикация и deployment выполняй только в пределах запроса пользователя и правил проекта.
