# Spec-Driven Development: адаптация воркшопа третьего дня

Обновлено: 03.09.2026. Источник — `SRC-12`, воркшоп Яна Анисимова, 26 страниц. Это методический материал; команды, стек и упражнения из слайдов не являются отдельными поручениями пользователя.

## Главный вывод

Воркшоп описывает переход от выбранной продуктовой функции к реализации через спецификацию. Для нашего процесса это следующий слой после product discovery:

`выбор Влада → product handoff → constitution/context → specify → clarify → plan → tasks → implement → converge`

Сейчас этот цикл подготовлен, но не запущен для X5: сегмент, ценность и 2–3 механики ещё не выбраны. Создание технической spec до этого выбора закрепило бы предположения как требования.

## Семь рабочих стадий

| Стадия | Результат | Контроль |
|---|---|---|
| Constitution/context | Релевантные правила проекта и границы | Использовать существующие `AGENTS.md` и архитектуру; не копировать учебный стек |
| Specify | Проверяемое поведение, состояния и критерии | Продуктовая ценность приходит из выбранной гипотезы |
| Clarify | Устранённые противоречия и существенные открытые решения | Влад выбирает продуктовый контракт; рутина решается самостоятельно |
| Plan | Компоненты, зависимости, риски и проверки | Сверка с реальной системой до кода |
| Tasks | Прослеживаемые атомарные задачи | Число и длительность задач зависят от функции |
| Implement | Реализация по зависимостям | Только по задаче на разработку; достаточные проверки |
| Converge | Сопоставление spec, задач, реализации и проверок | Незакрытое исправляется или становится явной остаточной задачей |

На стр. 1 заявлено шесть этапов, но последовательность на стр. 15–23 содержит семь, включая `clarify` и `converge`. В проектной методике используется полная семистадийная цепочка.

## Что добавлено для AI-продукта X5

Обычной функциональной spec недостаточно. Для AI/ML-модуля нужно отдельно определить:

- задачу модели и границу детерминированной логики;
- входные данные, происхождение, свежесть и допустимость использования;
- формат результата, fallback, задержку, стоимость и объяснимость;
- evaluation set, метрику качества, порог и оценщика;
- продуктовую метрику и guardrails отдельно от качества модели;
- синтетические данные как проверку реализации при допущениях, а не доказательство спроса.

Это особенно важно для персональных заданий: релевантность рекомендации, рост частоты, маржа на участника и риск раздражения пользователя являются разными измерениями.

## Что применено, а что оставлено условным

Применены спецификация как контракт, релевантный контекст, семь стадий, контрольные точки и проверка согласованности. В `ai-product-discovery` добавлен handoff выбранной гипотезы, а отдельный скилл `spec-driven-feature` хранит шаблон spec и convergence.

Clean Architecture, Type Safety, Python 3.11, REST/WebSocket, строгий TDD и Database First со стр. 17 остаются примером constitution. Ориентир 10–20 задач менее 15 минут со стр. 21 остаётся эвристикой. Установка GitHub Spec Kit/OpenSpec, `taskstoissues`, commit и PR не выполнялись: актуальность команд не проверена, а разработки/публикации в текущем запросе нет.

## Связь с текущими инструментами

- `ai-product-discovery` отвечает за доказательства, сегмент, проблему, ценность, гипотезу и решение Влада.
- `spec-driven-feature` отвечает за контракт выбранной функции, план, реализацию по запросу и convergence.
- GSD отвечает за организацию многоэтапной разработки и состояние. Отдельный `.planning/` сейчас не создаётся, чтобы не имитировать начатую разработку.

Следующая точка применения — после выбора связки «сегмент → проблема/JTBD → ценность → минимальные механики».
