## User Scenarios & Testing *(mandatory)*

### User Story 1 - Service Health Verification (Priority: P1)

Разработчик или DevOps-специалист проверяет, что веб-сервис запущен и отвечает на запросы. Этот эндпоинт используется для мониторинга и smoke-тестирования после деплоя.

**Why this priority**: Базовая проверка работоспособности сервиса — первый шаг для любой последующей разработки. Без неё невозможно верифицировать, что сервис стартовал корректно.

**Independent Test**: Полностью тестируется вызовом одного HTTP-запроса к `/health` и проверкой ответа — без базы данных или бизнес-логики.

**Acceptance Scenarios**:

1. **Given** сервис запущен, **When** отправляется GET-запрос на `/health`, **Then** сервис возвращает HTTP 200 с JSON-телом, содержащим статус `"ok"`.
2. **Given** сервис запущен, **When** отправляется GET-запрос на `/health`, **Then** ответ возвращается менее чем за 500 мс.
3. **Given** сервис не запущен, **When** отправляется GET-запрос на `/health`, **Then** соединение не устанавливается (connection refused).

---

### User Story 2 - Database Connectivity (Priority: P2)

Разработчик убеждается, что сервис способен подключиться к базе данных и применить миграции схемы. Это необходимо для всех последующих фич, хранящих данные.

**Why this priority**: База данных — основа хранения пользовательских данных (история покупок, профили, челленджи). Без настроенного подключения невозможно строить бизнес-логику.

**Independent Test**: Тестируется запуском команды применения миграций и проверкой, что таблицы созданы в БД без ошибок.

**Acceptance Scenarios**:

1. **Given** настроены переменные окружения для подключения к БД, **When** запускается применение миграций, **Then** схема создаётся без ошибок.
2. **Given** применены миграции, **When** сервис стартует, **Then** подключение к БД устанавливается успешно и сервис отвечает на `/health`.
3. **Given** переменные окружения БД не настроены, **When** сервис стартует, **Then** сервис падает с понятным сообщением об ошибке конфигурации.

---

### Edge Cases

- Что происходит, если порт уже занят при запуске сервиса?
- Как сервис ведёт себя при недоступности базы данных после успешного старта?
- Что возвращает `/health`, если база данных недоступна — 200 или деградированный статус?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Сервис ДОЛЖЕН принимать HTTP-запросы на настраиваемом порту.
- **FR-002**: Сервис ДОЛЖЕН предоставлять публичный эндпоинт проверки работоспособности (`/health`), возвращающий JSON-статус.
- **FR-003**: Эндпоинт `/health` ДОЛЖЕН быть доступен без аутентификации.
- **FR-004**: Сервис ДОЛЖЕН подключаться к реляционной базе данных через переменные окружения.
- **FR-005**: Сервис ДОЛЖЕН поддерживать управление версиями схемы базы данных через миграции.
- **FR-006**: Все зависимости ДОЛЖНЫ быть зафиксированы и воспроизводимо устанавливаться через менеджер пакетов.
- **FR-007**: Сервис ДОЛЖЕН логировать запросы и ошибки в структурированном формате.
- **FR-008**: Конфигурация сервиса (хост БД, порт, секреты) ДОЛЖНА задаваться через переменные окружения, а не хардкодиться.

### Key Entities

- **Конфигурация приложения**: настройки подключения к БД, хост и порт сервиса, уровень логирования. Не хранится в БД, задаётся окружением.
- **Схема БД**: набор таблиц и миграций, отражающий модель данных проекта. Управляется через систему версионирования миграций.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Эндпоинт `/health` отвечает HTTP 200 менее чем за 500 мс при нормальной нагрузке.
- **SC-002**: Сервис стартует менее чем за 10 секунд после запуска команды.
- **SC-003**: Применение миграций с нуля завершается без ошибок менее чем за 30 секунд.
- **SC-004**: Разработчик может запустить сервис локально за ≤3 команды после клонирования репозитория.
- **SC-005**: При неверной конфигурации БД сервис выдаёт понятное сообщение об ошибке (не stack trace).

## Assumptions

- Целевая СУБД — PostgreSQL (стандарт для Python-бэкендов проекта согласно конституции).
- Запуск локально и в Docker-контейнере; production-деплой вне скоупа данной задачи.
- Аутентификация и бизнес-логика будут добавлены в последующих фичах; сейчас только инфраструктура.
- Сервис располагается в `web/` или `src/<service>/` согласно структуре, описанной в Backend Technical Standards конституции.
- Переменные окружения задаются через `.env`-файл в корне репозитория (не коммитится).
- Тесты для данной инфраструктурной задачи ограничены smoke-тестом эндпоинта `/health`.
