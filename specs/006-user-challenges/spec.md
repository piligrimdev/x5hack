# Feature Specification: Персональные челленджи (задания) для пользователей

**Feature Branch**: `006-user-challenges`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "Реализовать систему заданий: генерация 3 персональных челленджей после первой покупки, обновление прогресса при новых покупках, создание бонуса при выполнении, замена задания при истечении дедлайна 7 дней. Всегда ровно 3 активных задания. Обработка покупки — фоновая (celery), запись в БД — синхронно. Reasoning LLM логируется. Названия полей в API/БД/скрипте не переименовывать — использовать mapping; недостающие поля добавлять в БД (source of truth)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Первое задание после первой покупки (Priority: P1)

Новый пользователь только что зарегистрировался и получил карту лояльности — истории покупок у него нет, активных заданий — тоже. При первой же совершённой покупке система инициирует генерацию 3 персональных заданий, используя эту покупку как стартовую точку истории. В приложении пользователь видит 3 задания с описанием, наградой в рублях и дедлайном 7 дней.

**Why this priority**: Это точка «aha!» для нового пользователя — принцип I конституции («экономия как видимая метрика»). Без появления заданий после первой же покупки механика для новичка не работает вообще.

**Independent Test**: Зарегистрировать пользователя, отправить через кассу один чек с его картой, дождаться фоновой обработки, запросить `GET /challenges/current` — увидеть 3 задания со статусом «открыто», дедлайном через 7 дней и заполненным описанием/наградой.

**Acceptance Scenarios**:

1. **Given** только что зарегистрированный пользователь без активных заданий, **When** касса создаёт первый чек с его loyalty_card_id, **Then** в течение 30 секунд после ответа API у пользователя появляется ровно 3 активных задания со статусом «открыто».
2. **Given** пользователь с пустой историей покупок, **When** для него генерируются задания на основе одной первой покупки, **Then** система принимает, что LLM/детерминированные пути имеют право деградировать к дженерик-предложениям — задания всё равно создаются, ни одно из 3 мест не остаётся пустым.
3. **Given** ответ на POST /receipts, **When** касса получает 201/200, **Then** ответ не блокируется генерацией заданий — запись чека завершается синхронно, генерация уходит в фон.

### User Story 2 — Прогресс задания и выдача награды (Priority: P1)

Пользователь с активными заданиями совершает следующую покупку. Каждая позиция чека сверяется с критерием каждого открытого задания. Если критерий совпал — прогресс задания растёт. Когда прогресс достиг цели, задание переводится в статус «выполнено», и в БД создаётся обещанная награда (например, персональная скидка), доступная пользователю.

**Why this priority**: Без выдачи награды за выполнение задание — пустой UI-элемент, механика не превращается в «видимую экономию» (принцип I) и не оправдывает своей стоимости (принцип IV).

**Independent Test**: Задать пользователю задание с критерием «product=X, quantity_target=2»; отправить чек, содержащий 2 единицы продукта X; убедиться, что задание перешло в «выполнено» и в БД появилась связанная награда, доступная пользователю.

**Acceptance Scenarios**:

1. **Given** активное задание с criterion_type=product, criterion_entity_id=<id>, quantity_target=2, quantity_current=0, **When** пользователь покупает 2 единицы этого продукта в одном чеке, **Then** задание получает quantity_current=2 и статус «выполнено».
2. **Given** активное задание с criterion_type=category, criterion_entity_id=<id категории>, quantity_target=1, **When** пользователь покупает любой товар этой категории, **Then** задание получает quantity_current≥1 и статус «выполнено».
3. **Given** задание переведено в «выполнено» после обработки чека, **When** транзакция обработки завершается, **Then** в БД создаётся запись награды, связанная с этим пользователем и этим заданием; обе операции атомарны (либо обе успешны, либо ни одна).
4. **Given** один чек, удовлетворяющий сразу нескольким активным заданиям, **When** обработчик запускается, **Then** каждое подходящее задание получает свой инкремент прогресса; двойной учёт одной позиции для одного задания невозможен.
5. **Given** пользователь совершает покупку, **When** касса отправляет чек, **Then** ответ API возвращается сразу после записи чека; апдейт статусов заданий и создание наград происходят фоновой задачей.

### User Story 3 — Истечение задания и автозамена (Priority: P2)

Задание, которое пользователь не выполнил за 7 дней с момента выдачи, переводится в статус «истекло». В этот момент система автоматически генерирует одно новое задание на его место, чтобы у пользователя всегда было ровно 3 активных задания.

**Why this priority**: Без «свежести» задания застоятся, счётчик из 3 «пустеет», и продукт перестаёт стимулировать возвращение пользователя. Замена — обязательное условие «всегда 3 активных».

**Independent Test**: Создать задание с дедлайном в прошлом, запустить sweep-обработчик, проверить: старое задание переведено в «истекло», новое задание с новым дедлайном создано; итого 3 активных.

**Acceptance Scenarios**:

1. **Given** активное задание с прошедшим дедлайном, **When** периодическая проверка запускается, **Then** задание переводится в «истекло», и в течение 5 минут создаётся ровно одно новое задание того же пользователя.
2. **Given** у пользователя было 3 активных задания, одно истекло, **When** истечение обработано, **Then** у пользователя снова 3 активных задания.
3. **Given** несколько заданий пользователя истекли одновременно, **When** истечение обработано, **Then** генерируется столько же новых заданий, сколько истекло — суммарно снова 3 активных.

### User Story 4 — Просмотр текущих заданий (Priority: P2)

Пользователь в мобильном приложении открывает раздел «Задания» и видит 3 текущих активных задания: название, описание, обещанную награду в рублях, прогресс (например, «1 из 2») и оставшееся время до дедлайна.

**Why this priority**: Без экрана заданий пользователь не знает, что задание существует, и мотивационный контур не замыкается. Экран должен быть достижим за ≤2 действия от главного экрана (принцип II).

**Independent Test**: Пользователь с 3 активными заданиями отправляет `GET /challenges/current` с валидным JWT → получает список из 3 объектов, каждый с полями title, description, reward, quantity_current, quantity_target, deadline, status.

**Acceptance Scenarios**:

1. **Given** пользователь с 3 активными заданиями, **When** запрашивает список текущих заданий, **Then** возвращаются 3 объекта с наглядным описанием, наградой и прогрессом.
2. **Given** пользователь только что зарегистрирован и не совершил ни одной покупки, **When** запрашивает список текущих заданий, **Then** возвращается пустой список с явным флагом «истории пока нет, задания появятся после первой покупки», без ошибок.
3. **Given** пользователь считается «saturated» (высокая частота покупок — скрипт вернул `no_challenge`), **When** запрашивает список активных заданий, **Then** возвращается 0..3 задания с явным флагом состояния «вы уже топ-покупатель, новых заданий сейчас нет» (либо чистый пустой список с этим маркером), без ошибок.
3. **Given** пользователь без карты лояльности (анонимный), **When** обращается к списку заданий без валидного JWT, **Then** запрос отклоняется с 401.

### User Story 5 — Аудит генерации: reasoning LLM сохранён (Priority: P3)

Каждый вызов скрипта генерации сохраняет: prompt, ответ модели, распарсенный reasoning, выбранный path (`personal`/`generic`/`generic_fallback`/`no_challenge`), название модели и attempt_id. Это нужно для анализа качества (hit rate ≥70% — принцип III) и последующей интеграции с Langfuse.

**Why this priority**: Требование принципа III («ИИ-персонализация с верифицируемым hit rate») — без логов reasoning невозможно оценить качество генерации. Не блокирует MVP, но обязательно к концу PoC.

**Independent Test**: Триггернуть генерацию задания для тестового пользователя; проверить, что в таблице логов появилась запись с prompt, response, reasoning, path, model, timestamp и task_id (если задание было создано).

**Acceptance Scenarios**:

1. **Given** запуск фоновой генерации задания, **When** генерация завершается любым исходом (успех / фолбэк / no_challenge), **Then** в системе аудита появляется запись с prompt, ответом модели, reasoning, path и model.
2. **Given** генерация упала в fallback из-за ошибки LLM, **When** аудитор смотрит запись, **Then** видно и запрос, и текст ошибки, и итоговый использованный path.

---

### Edge Cases

- **Первая покупка, но истории почти нет** — скрипт `synth/challenges.py::compute_receptiveness` требует ≥15 чеков за train-период. При 1 чеке пользователь не «receptive» → все 3 задания придут из детерминированных путей (spend_threshold, category_expansion) или дженерик-пула. Это ожидаемое поведение, не ошибка.
- **Скрипт вернул `path="no_challenge"` (пользователь «saturated», покупает уже часто)** — но по бизнес-правилу у нас всегда 3 активных задания. См. Q2 в Clarifications.
- **Позиция чека — товар из forbidden_categories (алкоголь и т.п.)** — скрипт не должен предлагать задания на эти категории; если позиция попала в чек, она не должна двигать прогресс задания, даже если случайно совпала по criterion.
- **Две покупки пользователя обрабатываются параллельно** — риск двойного инкремента прогресса. Обработчик должен использовать блокировку на уровне пользователя (или атомарные апдейты) для предотвращения race-condition.
- **Задание завершено, но создание награды упало (например, недоступен каталог продуктов для скидки)** — вся операция должна откатиться; задание не переводится в «выполнено», пока награда не создана атомарно.
- **Одна и та же позиция чека удовлетворяет 2 разным заданиям** — оба задания получают свой инкремент; двойной учёт для одного задания невозможен (позиция учитывается один раз на задание).
- **LLM API недоступен или вернул невалидный JSON** — скрипт уже фолбэчит на дженерик. Задание всё равно создаётся, path=`generic_fallback`, reasoning содержит текст ошибки.
- **Существующий пользователь (импортирован через seed_receipts, есть история чеков, нет заданий)** — при первом же триггере (покупка или запрос `GET /challenges/current`) получает 3 задания на основе всей его истории.
- **Продукт из LLM-ответа (favorite_item / novel_item) не найден в каталоге по имени** — маппинг деградирует до criterion_type=category. Задание всё равно валидно.
- **Пользователь удалил карту лояльности во время генерации** — фоновая задача видит отсутствие карты, тихо завершается, ничего не пишет.
- **Дубликат чека (тот же idempotency-key)** — не должен повторно инкрементить прогресс. Опора на существующую идемпотентность POST /receipts.
- **Пользователь получил задание «купить X», выполнил, получил награду (скидку на X). Использует эту скидку в следующей покупке.** — Позиция с применённой наградной скидкой всё равно должна нормально учитываться для других активных заданий, если совпадает по критерию.
- **Reward = скидка с ограниченным сроком** — если пользователь не использовал награду до её истечения, награда просто становится неактивной; статус задания остаётся «выполнено», нового задания взамен не выдаётся (замена — только по expiration задания, не по истечению награды).

## Requirements *(mandatory)*

### Functional Requirements

**Генерация и жизненный цикл заданий**

- **FR-001**: Система ДОЛЖНА поддерживать инвариант «у каждого пользователя с картой лояльности, имеющего хотя бы 1 чек, всегда ровно 3 активных задания» (статус «открыто»). Инвариант НЕ применяется в двух случаях: (а) у пользователя ещё нет ни одного чека; (б) скрипт признал пользователя «saturated» (см. FR-022) — тогда допустимо, чтобы у пользователя было 0 активных заданий и они не генерировались до тех пор, пока saturation не спадёт (следующая проверка при новом чеке или по расписанию).
- **FR-002**: Система ДОЛЖНА триггерить фоновую генерацию задания при следующих событиях: (а) успешное создание первого чека пользователя; (б) перевод любого активного задания в статус «выполнено»; (в) перевод любого активного задания в статус «истекло». Событие «первый чек» генерирует 3 задания; события (б) и (в) — по одному на замену.
- **FR-003**: Каждое задание ДОЛЖНО иметь дедлайн = issued_at + 7 календарных дней.
- **FR-004**: Активное задание, у которого deadline < текущее время, ДОЛЖНО быть переведено в статус «истекло» не позднее чем через 5 минут после наступления дедлайна.
- **FR-005**: 3 задания, генерируемые единовременно (например, после первого чека или после массового истечения), ДОЛЖНЫ различаться по механике или критерию — недопустимо создавать 3 задания с одинаковым (criterion_type, criterion_entity_id).
- **FR-005a**: Стратегия батча для 3 заданий одного пользователя — **mix из трёх типов скрипта**: одно задание генерируется с `challenge_type="llm"`, одно — с `challenge_type="spend_threshold"`, одно — с `challenge_type="category_expansion"`. `synth/challenges.py` не модифицируется. Разнообразие FR-005 достигается конструктивно (три разных пути дают три разных `mechanic`). Порядок вызовов может быть последовательным или параллельным (уточняется на /plan). При падении любого из путей — скрипт сам фолбэчит на generic (`path='generic_fallback'`), место в тройке всё равно заполняется. Для «замены одного истёкшего/выполненного задания» (не батч) — выбирается тип, который у пользователя сейчас отсутствует среди активных; если все три уже присутствуют — берётся тот, чей активный «партнёр» был закрыт последним.

**Прогресс и завершение**

- **FR-006**: При обработке нового чека completion-checker ДОЛЖЕН вычислить состояние каждого активного задания как логическое AND всех записей `task_criterion` этого задания (см. FR-023). Значение `task.quantity_current` обновляется на инкремент «сколько позиций/суммы/чеков засчитано» для основного kind задания, но окончательное решение о completion принимается по AND всех критериев, а не только по (quantity_current ≥ quantity_target).
- **FR-007**: Как только все `task_criterion` задания одновременно выполнены, статус задания ДОЛЖЕН быть переведён в «выполнено». Значение `quantity_current` при этом фиксируется на моменте, когда criterion был закрыт.
- **FR-008**: Позиция чека, товар которой относится к forbidden_categories (список из конфигурации скрипта), НЕ ДОЛЖНА двигать прогресс ни одного задания.
- **FR-009**: Один и тот же чек НЕ ДОЛЖЕН учитываться дважды для одного задания (дедупликация — по receipt_id).

**Награда**

- **FR-010**: При переводе задания в статус «выполнено» система ДОЛЖНА атомарно создать запись награды, связанную с этим пользователем и этим заданием. Если создание награды провалилось, задание ДОЛЖНО остаться в статусе «открыто» до успешного ретрая.
- **FR-011**: Форма награды при выполнении задания в MVP — запись в существующей таблице `discounts` c `discount_type='персональная'`, `loyalty_card_id=<user>`, `valid_to=issued_at + N дней` (N уточняется на /plan), `link_type` и `entity_id` — из `criterion_type`/`criterion_entity_id` задания, `scope='all'`. Скрипт возвращает только `reward_rub` (сумма) и `mechanic` (свободный текст); machine-readable «типа награды» скрипт не даёт, поэтому в MVP mapping-слой всегда создаёт Discount. Ограничение: `discounts.value` в текущей схеме — процент; правило вычисления `value` из `reward_rub` (в т.ч. потенциальное расширение схемы `discounts` на `value_type ∈ {percent, fixed_rub}` из BACKLOG) фиксируется на этапе /plan.
- **FR-011a** (мост для будущих типов наград): Task ДОЛЖНА иметь два поля — `reward_id UUID NULL` (в MVP указывает на `discounts.id`, без FK-constraint) и `reward_type VARCHAR NOT NULL DEFAULT 'discount'`. В MVP допустимое значение только `'discount'`. Введение новых типов (`coupon`, `points`) в будущем расширяет enum и добавляет отдельные таблицы без миграции Task. Mapping-слой сохраняет `mechanic` скрипта в отдельном `task.mechanic` поле как отображаемый текст, независимо от `reward_type`.

**Асинхронная обработка**

- **FR-012**: Обработчик POST /receipts ДОЛЖЕН синхронно записать чек в БД, вернуть ответ клиенту и поставить фоновую задачу «обработать чек» (обновление статусов заданий + генерация при необходимости). Ответ API НЕ должен ждать завершения фоновой обработки.
- **FR-013**: Фоновая обработка ДОЛЖНА быть идемпотентной: повторный запуск на том же receipt_id не должен приводить к двойному инкременту прогресса.
- **FR-014**: При параллельной обработке нескольких чеков одного пользователя обновление прогресса заданий ДОЛЖНО быть согласованным. Механизм: обработчик чека в начале транзакции берёт pessimistic row-lock на владельца задания (`SELECT ... FROM users WHERE id = :user_id FOR UPDATE`). Все чеки одного пользователя обрабатываются последовательно; чеки разных пользователей — параллельно. Дополнительно — уникальный индекс `UNIQUE(task_id, receipt_id)` на сущности `task_receipt_increment` (см. FR-025) гарантирует идемпотентность на случай повторной обработки одного и того же чека.
- **FR-025**: Система ДОЛЖНА иметь сущность `task_receipt_increment(task_id FK, receipt_id FK, applied_at, PRIMARY KEY(task_id, receipt_id))` — дедупликационная таблица «этот чек уже учтён этим заданием». Обработчик чека перед инкрементом проверяет наличие пары; после успешного инкремента — вставляет строку в той же транзакции. Повторный запуск фоновой задачи на том же receipt_id не приведёт к двойному инкременту благодаря уникальности PK.

**Пользовательские эндпоинты**

- **FR-015**: Авторизованный пользователь ДОЛЖЕН получать список своих активных заданий (`GET /challenges/current` или аналог), включающий title, description, reward description, quantity_current, quantity_target, deadline, status для каждого. Максимум 3 задания в ответе.
- **FR-016**: Пользователь без ни одного чека ДОЛЖЕН получать пустой список активных заданий с явным индикатором «истории пока нет».
- **FR-017**: Запросы к эндпоинту заданий без валидного JWT ДОЛЖНЫ отклоняться с 401.

**Аудит и логирование**

- **FR-018**: Каждый вызов скрипта генерации ДОЛЖЕН быть залогирован с полями: user_id, timestamp, model (для LLM-путей), prompt, response, path (из выхода скрипта), reasoning, task_id (если задание создано) или error (если фолбэк). Логирование выполняется в БД для аудита; интеграция с Langfuse — BACKLOG.

**Схема данных и маппинг**

- **FR-019**: Названия полей в существующих сущностях (Receipt, ReceiptItem, Discount, LoyaltyCard, Product, Category) НЕ ДОЛЖНЫ переименовываться под нужды скрипта генерации. Разница схем скрипт↔БД разрешается mapping-слоем.
- **FR-020**: Недостающие для генерации/жизненного цикла заданий поля ДОЛЖНЫ добавляться в БД (БД = source of truth): в частности, для сущности `task` — как минимум `title`, `description`, `mechanic`, `reward_rub`, `reasoning`, `path`, `model`. Для reward — согласно решению FR-011. Для аудита — отдельная сущность (см. FR-018).
- **FR-021**: Маппинг выхода скрипта `generate_challenge_for_user` → сущность `task` + одна или несколько строк `task_criterion` (см. FR-023):
  - Основной criterion задания (обязательный) кладётся в поля Task: `criterion_type`, `criterion_entity_id`, `quantity_target`. Значение основного criterion:
    - Если у результата есть `favorite_item` (спенд-порог) или `novel_item` (расширение категорий) — искать Product по имени в целевой категории → criterion_type='product', criterion_entity_id=product.id. Если продукт не найден — фолбэк на criterion_type='category', criterion_entity_id=id первой из `target_categories`.
    - Если продукта нет — использовать criterion_type='category', criterion_entity_id=id первой из `target_categories`.
    - criterion_type='brand' в PoC не используется.
    - `quantity_target=1` по умолчанию.
  - Дополнительные критерии (пример: `spend_threshold_rub` из `build_spend_threshold_challenge`) кладутся в `task_criterion` как отдельные строки — по одной на kind.
  - Будущее расширение JSON-схемы LLM (планируется другой разработчик, имя поля TBD) требует ТОЛЬКО правки адаптера: добавляется новая ветка «если поле X в JSON — kind='X', value=…»; миграция схемы `task_criterion` не нужна, потому что она EAV.
- **FR-022**: Если скрипт вернул `path="no_challenge"` для запроса на генерацию — задание НЕ создаётся, слот остаётся пустым, saturation-факт логируется в `challenge_generation_log` (см. FR-018) с path='no_challenge' и `task_id=NULL`. Пользователь может иметь 0, 1, 2 или 3 активных задания в этом состоянии — инвариант FR-001 к нему не применяется. Повторная попытка генерации для saturated-пользователя триггерится по обычным событиям (новый чек / истечение старого задания / периодическая проверка), и при снятии saturation обычная генерация возобновляется.
- **FR-023**: Система ДОЛЖНА иметь сущность `task_criterion` (EAV-таблица): `id, task_id FK, kind VARCHAR NOT NULL, key VARCHAR NULL, value_num NUMERIC NULL, value_text VARCHAR NULL, created_at`. Одно задание — одна или несколько строк. Известные `kind` в MVP: `item_quantity` (для quantity-based; value_num = quantity_target для основного criterion, дублируется на Task для обратной совместимости с `context/schema.md`), `spend_threshold_rub` (для пути `spend_threshold`; value_num = порог в рублях). Новые `kind` (от расширений LLM-схемы) добавляются без миграции — адаптер знает, что писать; completion-checker знает, что проверять.
- **FR-024**: Completion-checker для каждого известного `kind` реализует чистую функцию `(task, task_criterion, receipt) -> bool` («выполнен ли этот критерий с учётом нового чека»). Задание считается выполненным ТОЛЬКО когда все связанные с ним `task_criterion` возвращают True. Незнакомый `kind` (когда коллега добавил новое поле в LLM-схему, но соответствующий checker ещё не реализован) обрабатывается как «критерий никогда не выполним» — задание не может быть закрыто, factuality о неизвестном kind логируется через structlog. Это защита от «выдать награду по неполной проверке».

### Key Entities *(include if feature involves data)*

- **Task (Задание)**: экземпляр челленджа, привязанный к loyalty_card. Существует в схеме (`context/schema.md`); недостающие поля добавляются в БД: `title`, `description`, `mechanic` (текстовое описание из скрипта), `reward_rub` (сумма из скрипта, храним на задании отдельно от Discount.value для аудита), `reasoning`, `path`, `model`, `reward_type VARCHAR default 'discount'`, `reward_id UUID NULL` (без FK; в MVP — указатель на `discounts.id`). Основной критерий продолжает жить в полях `criterion_type` + `criterion_entity_id` + `quantity_target` (совместимо с `context/schema.md`); дополнительные критерии — в `task_criterion` (см. FR-023).
- **TaskCriterion (Критерий задания)**: EAV-запись критерия, привязанная к Task. Поля: `id, task_id, kind, key, value_num, value_text, created_at`. Одно задание = 1..N строк. Позволяет добавлять новые типы условий (spend_threshold, будущие расширения LLM-схемы) без миграции. См. FR-023, FR-024.
- **TaskReceiptIncrement (Учёт применения чека)**: `task_id, receipt_id, applied_at`, PK(task_id, receipt_id). Дедупликация: чек не может быть учтён одним заданием дважды. См. FR-025.
- **TaskStatus (Статус задания)**: словарь `открыто / выполнено / провалено / истекло` (из схемы).
- **Reward (Награда)**: в MVP — запись в существующей таблице `discounts` (`discount_type='персональная'`, `loyalty_card_id`, `valid_to`, `link_type` и `entity_id` из criterion задания). Связь с задачей — через `task.reward_type='discount'` + `task.reward_id`. Мост FR-011a допускает будущие альтернативные сущности (Coupon, Points) без изменения схемы Task.
- **ChallengeGenerationLog (Лог генерации)**: аудит-запись каждого вызова скрипта генерации (см. FR-018). Новая сущность.
- **LoyaltyCard**: существует; связывает пользователя с заданиями и наградами.
- **Receipt / ReceiptItem / Product / Category**: существуют; читаются mapping-слоем для формирования dict-профиля и для сверки прогресса заданий.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Новый пользователь видит 3 активных задания не позднее чем через 30 секунд после ответа API на его первый чек.
- **SC-002**: 100% квалифицирующих позиций чека приводят к инкременту прогресса соответствующих активных заданий (проверяется на пуле из ≥50 тестовых чеков).
- **SC-003**: При выполнении задания награда создаётся в 100% случаев атомарно с изменением статуса; нет ни одного «висящего» выполненного задания без награды.
- **SC-004**: 100% истёкших заданий заменяются новым не позднее чем через 5 минут после наступления дедлайна.
- **SC-005**: POST /receipts возвращает ответ за ≤ 2 секунд в 95% случаев независимо от загруженности фоновой обработки.
- **SC-006**: 100% вызовов скрипта генерации имеют соответствующую запись в аудит-логе с prompt, response, path, model и reasoning (или ошибкой).
- **SC-007**: `GET /challenges/current` возвращает ответ за ≤ 500 мс в 95% случаев.
- **SC-008**: У пользователя (с ≥1 чеком, не saturated) не наблюдается >3 или <3 активных заданий более 5 минут подряд. Для saturated-пользователей (см. FR-022) допустимо 0–3.
- **SC-009**: LLM hit rate на 30–50 эталонных профилях остаётся ≥70% (принцип III конституции) — метрика проверяется офлайн-скриптом, не в рантайме API.

## Assumptions

- Скрипт `synth/challenges.py` (существующий) используется как единая точка генерации персонального челленджа. Все три его пути (`llm`, `spend_threshold`, `category_expansion`) доступны и выбираются mapping-слоем в веб-сервисе.
- Из «истории покупок», передаваемой скрипту, берётся вся история пользователя за 90 дней (train-window скрипта), включая только что записанный чек, — а не только этот единственный чек.
- Существующие карты лояльности, импортированные через `seed_receipts.py`, получают свои 3 стартовых задания лениво — при первом же триггере (новая покупка или запрос списка заданий), но НЕ через массовый бэкфилл при выкатке.
- Для форматирования задания в API-ответе используются производные от полей БД поля (title/description/reward_rub из БД, «сколько дней осталось» — вычисляется из deadline). Отдельного «read model» нет.
- Первые 3 задания после первого чека новичка могут все быть детерминированными/дженериковыми — это ожидаемая деградация, не ошибка (см. Edge Cases). Персонализация улучшается по мере накопления истории.
- Логирование reasoning в PoC — таблица в PostgreSQL + `structlog`. Интеграция с Langfuse (tool-call трейсинг) — BACKLOG.
- Периодическая проверка на истечение заданий выполняется каждые ~1–5 минут; точность «секунда-в-секунду» не требуется.
- Все даты (issued_at, deadline) — в UTC на уровне БД, в API возвращаются в ISO 8601 с TZ.
- Reward, будучи связанной с task, наследует ограничение: одна выполненная задача = максимум одна награда. Множественные награды за одно задание не создаются.
- Мобильный клиент опрашивает `GET /challenges/current` при открытии соответствующего экрана и не полагается на push (BACKLOG). TTL кэша на клиенте — до конца суток (см. ARCHITECTURE.md).
- Интеграция скрипта в web-сервис допускает как импорт `synth` пакета в web-образ, так и вынесение общего кода в отдельный пакет — выбор — на стадии /plan.

## Clarifications

### Session 2026-09-04

- Q: В какой форме создаётся награда за выполнение задания? → A: Existing `discounts` (переиспользуем сущность с `loyalty_card_id`, `discount_type='персональная'`), + архитектурный мост `task.reward_type` / `task.reward_id` для будущих типов (Coupon, Points). Обоснование: `synth/challenges.py` возвращает только `reward_rub` (сумма) и `mechanic` (свободный текст); машинного «типа награды» скрипт не даёт, все пути фактически описывают вариации скидки. Правило конвертации `reward_rub` → `discounts.value` уточняется на /plan.
- Q: Как реагировать на `path="no_challenge"` от скрипта? → A: Разрешить <3 активных заданий для saturated-пользователей — ослабляем инвариант FR-001 (исключение (б)). Задание не создаётся, факт логируется в `challenge_generation_log`. Фронт рендерит явное пустое состояние («вы уже топ-покупатель, новых заданий сейчас нет»). Повторная генерация — при следующем чеке / периодической проверке; если saturation снялся — обычная генерация возобновляется.
- Q: Как поддержать разные типы критериев (item quantity vs spend threshold) и будущее расширение LLM JSON-схемы? → A: EAV-таблица `task_criterion(id, task_id, kind, key, value_num, value_text, created_at)`. Основной criterion остаётся в полях Task (совместимость с `context/schema.md`); дополнительные — как отдельные строки. Completion-checker роутит по `kind`. Незнакомый `kind` = «не выполнено», задание не закрывается. Новое поле в LLM-схеме не требует миграции, только правки адаптера (FR-023, FR-024).
- Q: Как защищаться от race-condition при параллельной обработке чеков одного пользователя? → A: Pessimistic per-user row-lock (`SELECT ... FROM users WHERE id=:user_id FOR UPDATE`) в начале транзакции воркера. Все чеки одного пользователя сериализуются, разные пользователи — параллельно. Дополнительно — сущность `task_receipt_increment` с PK(task_id, receipt_id) для идемпотентности повторной обработки одного и того же чека (FR-014, FR-025).
- Q: Как батчить генерацию 3 заданий на одного пользователя, учитывая что скрипт возвращает по одному заданию за вызов? → A: Mix из трёх типов — 1×`llm` + 1×`spend_threshold` + 1×`category_expansion`. Скрипт не модифицируется. Разнообразие FR-005 конструктивно (разные `mechanic`), LLM-cost 1× на батч, при падении LLM у пользователя всё равно 2 из 3 detereministic-заданий. Для одиночной замены — выбирается тип, отсутствующий среди активных (FR-005a).
