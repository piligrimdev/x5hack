# Спецификация Функции: Инфраструктура Наблюдаемости и Мониторинга

**Ветка Функции**: `001-add-observability-infrastructure`

**Создано**: 2026-09-05

**Статус**: Черновик

**Исходное описание**: "Необходимо добавить инфраструктуру к нашему приложению - grafana + loki + promtail для structlog и метрик, langfuse для отслеживания prompt, completion, function calls и token usage на юзера, flower для работы с celery shared task. проверь текущую реализацию в web, она должна быть готова к интеграции этих сервисов. Дашборды grafana необходимо будет обсудить в clarify, как и работу с запроссами к openrouter и langfuse."

## Пользовательские Сценарии и Тестирование *(обязательно)*

### Сценарий 1 - DevOps инженер мониторит здоровье системы (Приоритет: P1)

DevOps инженер должен наблюдать здоровье приложения в реальном времени: latency API запросов, уровень ошибок, выполнение рабочих задач и потребление ресурсов. Без централизованного мониторинга проблемы остаются невидимыми до тех пор, пока пользователи не сообщат о них.

**Почему этот приоритет**: Наблюдаемость production критична для поддержания надежности системы и отладки проблем в реальном времени.

**Независимый тест**: Полностью тестируется установкой дашбордов Grafana, которые агрегируют метрики от работающих сервисов и отображают здоровье системы в реальном времени.

**Сценарии приемки**:

1. **Дано** API, worker и база данных работают, **Когда** метрики отправляются на Prometheus-совместимый endpoint, **Тогда** Grafana отображает текущие CPU, memory, количество запросов и уровень ошибок
2. **Дано** пользователи делают запросы к API, **Когда** запросы завершаются, **Тогда** latency и статус код логируются и видны на дашборде
3. **Дано** работают несколько Celery workers, **Когда** задачи выполняются, **Тогда** Flower UI показывает глубину очереди, статус worker и уровни завершения

---

### Сценарий 2 - Backend разработчик отлаживает ошибки запросов (Приоритет: P1)

Backend разработчик должен трейсировать структурированные логи от FastAPI сервиса в течение жизненного цикла запроса. Когда пользователь сообщает о проблеме, разработчик должен найти все записи логов (entry/exit точки, DB запросы, внешние API вызовы) для этого пользователя в одном месте.

**Почему этот приоритет**: Структурированное логирование необходимо для быстрой диагностики проблем и повышения производительности разработчика.

**Независимый тест**: Полностью тестируется запуском приложения с Loki + Promtail стеком и проверкой того, что все structlog записи появляются в Grafana Loki с searchable labels (user_id, request_id, service).

**Сценарии приемки**:

1. **Дано** сервис отправляет структурированные логи через structlog, **Когда** логи собираются Promtail, **Тогда** они появляются в Loki с queryable labels в течение 5 секунд
2. **Дано** пользователь делает запрос, **Когда** запрос завершается, **Тогда** разработчик может поискать в Loki по user_id и увидеть все записи логов для этого запроса
3. **Дано** приложение крашится или выбрасывает исключение, **Когда** разработчик ищет по типу ошибки в Loki, **Тогда** stack trace и контекст присутствуют

---

### Сценарий 3 - ML инженер мониторит производительность LLM модели (Приоритет: P1)

ML инженер должен отслеживать каждый LLM API вызов сделанный системой: input токены, output токены, latency модели, стоимость и уровень успеха, агрегированные по пользователю. Это позволяет атрибутировать стоимость, оценивать производительность модели и обнаруживать аномалии (например, пользователь отправляет 1000 вызовов за 5 минут).

**Почему этот приоритет**: Без LLM observability мы не можем контролировать стоимость, отлаживать проблемы качества модели или применять квоты использования.

**Независимый тест**: Полностью тестируется интеграцией Langfuse SDK, созданием LLM вызовов к OpenRouter и проверкой того, что трейсы появляются на дашборде Langfuse с user_id, количеством токенов, стоимостью и latency.

**Сценарии приемки**:

1. **Дано** сервис делает вызовы к OpenRouter LLM API, **Когда** вызовы завершаются, **Тогда** Langfuse получает трейс с названием модели, input/output токенами, latency и user_id
2. **Дано** пользователь делает несколько запросов, **Когда** трейсы агрегируются в Langfuse, **Тогда** видно общее использование токенов пользователя, стоимость и количество запросов
3. **Дано** LLM вызов не удается, **Когда** ошибка логируется, **Тогда** Langfuse показывает тип ошибки и контекст вместе с успешными трейсами

---

### Сценарий 4 - DevOps инженер мониторит очередь рабочих задач (Приоритет: P2)

DevOps инженер должен иметь видимость в выполнение Celery задач: глубину очереди, доступность worker, уровни успеха/неудачи и медленные задачи. Это позволяет планировать емкость и рано обнаружить накопление в очереди.

**Почему этот приоритет**: Без мониторинга очереди задач проблемы доступности worker остаются невидимыми до тех пор, пока пользователи не испытают ухудшение сервиса.

**Независимый тест**: Полностью тестируется запуском Flower UI, триггерингом Celery задач и проверкой того, что статус задач, глубина очереди и здоровье worker видны.

**Сценарии приемки**:

1. **Дано** Celery workers регистрируются с Redis broker, **Когда** открывается Flower, **Тогда** список показывает все активные workers и их статус (online/offline)
2. **Дано** задачи ставятся в очередь, **Когда** задачи выполняются, **Тогда** Flower показывает количество задач, время выполнения и статус успеха/неудачи
3. **Дано** очередь задач растет, **Когда** глубина очереди превышает порог, **Тогда** доступен alert для настройки DevOps

## Требования *(обязательно)*

### Функциональные Требования

- **FR-001**: Приложение ДОЛЖНО отправлять структурированные логи используя библиотеку `structlog` из всех Python сервисов с обязательными labels: `service_name`, `user_id`, `request_id`, `procedure_name`, `procedure_state`
- **FR-002**: Promtail ДОЛЖЕН собирать логи от FastAPI сервиса и пересылать их в Loki со всеми структурированными labels доступными для запроса
- **FR-003**: Grafana ДОЛЖНА иметь настроенные источники данных для запроса метрик из Prometheus и логов из Loki
- **FR-004**: Grafana ДОЛЖНА отображать три отдельных дашборда: (1) Здоровье & Производительность API (latency p50/p95, уровень ошибок по endpoint, количество запросов), (2) Очередь Задач Celery (глубина очереди, статус worker, время выполнения задач), (3) Использование LLM & Затраты (использование токенов по пользователю, атрибуция стоимости, уровень успеха вызовов)
- **FR-005**: Prometheus ДОЛЖЕН собирать стандартные HTTP метрики (количество запросов, latency, статус коды по endpoint) И custom application метрики (обработанные задачи, уровень успеха генерации модели, время расчета корзины)
- **FR-006**: Celery ДОЛЖЕН пересылать события задач в Flower UI для мониторинга задач в реальном времени
- **FR-007**: Langfuse SDK ДОЛЖЕН быть интегрирован в FastAPI сервис для отслеживания всех LLM API вызовов с user_id извлеченным из контекста запроса через contextvars
- **FR-008**: OpenRouter API вызовы ДОЛЖНЫ автоматически трейсироваться в Langfuse перед и после запроса с названием модели, input/output токенами, latency и user_id
- **FR-009**: Приложение ДОЛЖНО gracefully деградировать если Langfuse API недоступен (без краша, логирование в stdout как fallback)
- **FR-010**: Flower ДОЛЖЕН показывать статус очереди Celery, список worker и историю выполнения задач
- **FR-011**: Langfuse ДОЛЖЕН быть развернут как self-hosted сервис в docker-compose с PostgreSQL и vector базой данных
- **FR-012**: Все сервисы (API, workers, мониторинг стек включая Loki, Prometheus, Grafana, Flower, Langfuse) ДОЛЖНЫ быть запускаемы через `docker-compose` одной командой

### Ключевые Сущности *(включаются если фича задействует данные)*

- **Запись Лога**: Структурированная запись отправленная сервисом (название сервиса, временная метка, уровень лога, сообщение, labels как user_id, request_id)
- **Метрика**: Точка данных временного ряда (endpoint, метод, latency, статус код, временная метка)
- **LLM Трейс**: Запись одного LLM API вызова (модель, input токены, output токены, latency, стоимость, user_id, временная метка)
- **Задача Celery**: Асинхронная работа поставленная в очередь для выполнения (тип задачи, время постановки, время начала, время окончания, статус, ID worker)

## Критерии Успеха *(обязательно)*

### Измеримые Исходы

- **SC-001**: Все структурированные логи из API сервиса появляются в Loki в течение 5 секунд с отправкой со всеми обязательными labels (service_name, user_id, request_id, procedure_name, procedure_state) доступными для запроса
- **SC-002**: Дашборд Grafana API Health отображает latency p50/p95, уровень ошибок по endpoint и количество запросов без ручного запроса
- **SC-003**: Дашборд Grafana Celery Task Queue отображает глубину очереди, активных workers и время выполнения задач обновляемое в течение 10 секунд
- **SC-004**: Дашборд Grafana LLM Usage & Costs отображает использование токенов по пользователю, общую стоимость и уровень успеха вызовов агрегированные из Langfuse
- **SC-005**: Каждый LLM вызов к OpenRouter трейсируется в Langfuse с user_id (извлеченным из контекста запроса) и количеством токенов в течение 2 секунд
- **SC-006**: Flower UI показывает статус задач Celery в реальном времени и глубину очереди, обновляемые в течение 10 секунд
- **SC-007**: DevOps может идентифицировать и диагностировать ошибки API поиском логов по user_id в Loki в течение 1 минуты
- **SC-008**: ML команда может атрибутировать затраты на LLM пользователям через отчеты Langfuse в течение 1 дня после API вызова
- **SC-009**: Система остается работоспособной если backend Langfuse недоступен (нет увеличения уровня ошибок, нет потери запросов)
- **SC-010**: Custom application метрики (количество задач, уровень успеха генерации модели, время расчета корзины) экспортируются в Prometheus и видны на дашбордах

## Предположения

- **Хранилище мониторинга** out of scope для v1: Loki, Prometheus и Langfuse будут развернуты с политиками retention по умолчанию; политика production retention и archival будут настроены позже
- **Правила alert** out of scope для v1: Prometheus alerting в Slack/PagerDuty будет добавлено в follow-up задаче
- **Дизайн дашбордов Grafana**: Будут созданы три отдельных сфокусированных дашборда — (1) Здоровье & Производительность API, (2) Мониторинг Очереди Задач Celery, (3) Использование LLM & Затраты
- **Интеграция OpenRouter** уже на месте; эта задача добавляет только instrumentation observability вокруг существующих вызовов
- **Управление API ключом Langfuse** будет использовать переменные окружения; политика ротации секретов для production out of scope
- **Обратная совместимость** с существующей конфигурацией structlog в web сервисе требуется; нет breaking changes в logging API
- **Docker Compose** используется для локальной разработки и integration тестирования; развертывание Kubernetes out of scope
- **Развертывание Langfuse**: Self-hosted сервис Langfuse в docker-compose с локальной PostgreSQL и vector базой данных для фазы разработки/PoC
