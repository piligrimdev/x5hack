# Feature Specification: Покупки, магазины и скидки

**Feature Branch**: `005-purchases-stores-discounts`

**Created**: 2026-09-04

**Status**: Draft

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Касса: предварительный расчёт скидок (Priority: P1)

Кассовый аппарат передаёт список товаров с количеством и данные покупателя (карта лояльности). Сервер возвращает рассчитанную цену к оплате для каждого товара с учётом лучшей из доступных скидок.

**Why this priority**: Это ядро бизнес-логики — без корректного выбора скидки нет смысла фиксировать покупку.

**Independent Test**: Можно протестировать, отправив корзину с несколькими товарами и проверив, что возвращённые цены соответствуют best-price-wins логике.

**Acceptance Scenarios**:

1. **Given** покупатель с картой лояльности и корзина из 3 товаров, на один из которых есть персональная скидка, на второй — акционная скидка, на третий — скидки нет, **When** касса запрашивает расчёт, **Then** сервер возвращает для каждого товара: лучшую применимую скидку и итоговую цену к оплате.
2. **Given** товар, попадающий под несколько скидок одновременно (по продукту, по категории, по бренду), **When** касса запрашивает расчёт, **Then** применяется скидка с максимальным уменьшением цены (best-price-wins).
3. **Given** истёкшая скидка (valid_to в прошлом) или скидка, действующая в другом магазине, **When** касса запрашивает расчёт, **Then** эта скидка не применяется.
4. **Given** пользователь без карты лояльности (анонимный покупатель), **When** касса запрашивает расчёт, **Then** персональные скидки не применяются, только публичные акции.

---

### User Story 2 — Касса: фиксация покупки в системе (Priority: P1)

После подтверждения покупателем итоговой суммы касса отправляет финальный чек на сервер. Сервер сохраняет чек со всеми позициями, применёнными скидками, ценами на момент покупки.

**Why this priority**: Без фиксации покупки невозможно отобразить историю и экономию пользователя.

**Independent Test**: Отправить чек и убедиться, что он появился в хранилище с корректными данными (цена без скидки, фактическая цена, применённая скидка, дата, магазин).

**Acceptance Scenarios**:

1. **Given** корзина с рассчитанными скидками, покупателем и магазином, **When** касса отправляет чек, **Then** в системе создаётся запись чека с каждой позицией: base_price_at_purchase, paid_price, discounted_amount, discount_id.
2. **Given** позиция чека без применённой скидки, **When** чек сохраняется, **Then** discount_id = NULL, paid_price = base_price_at_purchase, discounted_amount = 0.
3. **Given** чек с тем же idempotency-key (UUID, переданным кассой) отправлен повторно, **When** сервер его обрабатывает, **Then** возвращается тот же ответ, что и при первом запросе, без создания нового чека.

---

### User Story 3 — Пользователь: просмотр истории покупок (Priority: P2)

Пользователь в мобильном приложении видит список своих чеков с детализацией по каждому и суммарной экономией.

**Why this priority**: Ключевая метрика продукта — видимая экономия (Принцип I конституции). Без этого экрана пользователь не видит ценность карты лояльности.

**Independent Test**: Авторизованный пользователь открывает раздел покупок и видит свои чеки с суммами экономии.

**Acceptance Scenarios**:

1. **Given** пользователь с несколькими совершёнными покупками, **When** открывает список чеков, **Then** видит дату, магазин, итоговую сумму и сумму сэкономленного по каждому чеку.
2. **Given** пользователь открывает конкретный чек, **When** смотрит детализацию, **Then** видит каждую позицию: название товара, количество, цену без скидки, цену со скидкой.
3. **Given** пользователь без истории покупок, **When** открывает раздел, **Then** видит пустой экран с приглашением совершить первую покупку.

---

### User Story 4 — Пользователь: суммарная экономия (Priority: P2)

Пользователь видит агрегированную цифру своей экономии за всё время или выбранный период — сумма полочных цен минус сумма фактически уплаченных.

**Why this priority**: Единая видимая метрика «сколько сэкономлено» — основной KPI продукта согласно Принципу I конституции.

**Independent Test**: Открыть дашборд экономии и проверить, что цифра соответствует сумме discounted_amount по всем чекам пользователя.

**Acceptance Scenarios**:

1. **Given** пользователь с тремя чеками с экономией 50, 120 и 30 рублей, **When** открывает дашборд экономии, **Then** видит «200 рублей сэкономлено».
2. **Given** пользователь просматривает экономию, **When** данные загружаются, **Then** цифра обновляется после каждой новой покупки без ручного обновления.

---

### User Story 5 — Просмотр магазинов и скидок (Priority: P3)

Любой пользователь (и касса) может получить список доступных магазинов и актуальных скидок.

**Why this priority**: Справочные данные, необходимые для корректного расчёта скидок и отображения в UI.

**Independent Test**: GET-запрос к магазинам/скидкам без авторизации или с любой авторизацией возвращает список.

**Acceptance Scenarios**:

1. **Given** неавторизованный запрос к списку магазинов, **When** запрос выполняется, **Then** возвращается список магазинов с id, форматом сети, геокластером.
2. **Given** запрос к списку скидок, **When** запрос выполняется, **Then** возвращаются только актуальные скидки (valid_from ≤ сегодня ≤ valid_to или valid_to = NULL).

---

### User Story 6 — Касса: управление магазинами и скидками (Priority: P3)

Кассовый аппарат (привилегированный клиент) может создавать и обновлять магазины и скидки.

**Why this priority**: Административная функция, нужна для наполнения справочников; в PoC может быть упрощена.

**Independent Test**: Авторизованная касса создаёт магазин и скидку — они появляются в списке.

**Acceptance Scenarios**:

1. **Given** авторизованная касса, **When** отправляет POST /stores, **Then** магазин создаётся и возвращается с присвоенным id.
2. **Given** неавторизованный клиент (обычный пользователь), **When** пытается создать магазин или скидку, **Then** получает 403 Forbidden.

---

### Edge Cases

- Если product_id из корзины не найден в каталоге (при расчёте или фиксации): возвращается 422 с перечнем неизвестных product_id; операция не выполняется.
- Если скидка истекла между расчётом (шаг 4) и фиксацией чека (шаг 5): сервер возвращает 422 с указанием конкретных позиций с истёкшими скидками; касса обязана перезапросить расчёт.
- Как система обрабатывает нулевое количество товара в позиции?
- Что возвращается, если loyalty_card_id не найден при расчёте?

## Requirements *(mandatory)*

### Functional Requirements

**Расчёт скидок (касса → сервер)**

- **FR-001**: Сервер ДОЛЖЕН принимать запрос на предварительный расчёт: loyalty_card_id (опционально), store_id, список {product_id, quantity}. Если хотя бы один product_id не найден — вернуть 422 с перечнем неизвестных id.
- **FR-002**: Для каждого товара сервер ДОЛЖЕН перебрать все применимые скидки (по product / category / brand) с учётом scope (all / by_format / by_store) и срока действия, выбрав ту, что минимизирует paid_price (best-price-wins).
- **FR-003**: Ответ на расчёт ДОЛЖЕН содержать для каждой позиции: product_id, base_price, paid_price, discount_id (или null), итоговую сумму чека.
- **FR-004**: Если loyalty_card_id не передан или не найден, персональные скидки (тип "персональная") не должны применяться.

**Фиксация чека (касса → сервер)**

- **FR-005**: Сервер ДОЛЖЕН принимать POST-запрос на создание чека: idempotency-key (UUID, обязательный заголовок), loyalty_card_id (опционально), store_id, channel, payment_card_uid (опционально), список {product_id, quantity, discount_id}.
- **FR-005a**: Сервер ДОЛЖЕН проверять idempotency-key: если чек с таким ключом уже создан, вернуть тот же ответ без повторной записи (идемпотентный POST).
- **FR-006**: Для каждой позиции сервер ДОЛЖЕН записать base_price_at_purchase (актуальная цена продукта на момент запроса), paid_price (с применённой скидкой), discounted_amount = base - paid, discount_id.
- **FR-007**: Если discount_id передан, сервер ДОЛЖЕН верифицировать, что эта скидка применима к данному продукту в данном магазине и актуальна на момент покупки. Если хотя бы одна переданная скидка истекла или неприменима — вернуть 422 с перечнем проблемных позиций; чек не сохраняется.
- **FR-008**: Сервер ДОЛЖЕН обновить прогресс (quantity_current) в активных заданиях (task) пользователя по позициям чека, если задание существует.

**История покупок (пользователь → сервер)**

- **FR-009**: Авторизованный пользователь ДОЛЖЕН получить список своих чеков (GET) с датой, магазином, суммой и экономией по чеку.
- **FR-010**: Авторизованный пользователь ДОЛЖЕН получить детализацию конкретного чека с позициями: название товара, количество, base_price, paid_price, discount.
- **FR-011**: Авторизованный пользователь ДОЛЖЕН получить агрегированную экономию: сумма всех discounted_amount по его чекам.

**Магазины и скидки**

- **FR-012**: GET /stores и GET /discounts ДОЛЖНЫ быть доступны без аутентификации (публичные эндпоинты).
- **FR-013**: POST /stores, PUT /stores/{id}, POST /discounts, PUT /discounts/{id}, POST /receipts и POST /receipts/calculate ДОЛЖНЫ требовать заголовок `X-Terminal-Token` с валидным статичным секретом (TerminalTokenDep); без него — 401.
- **FR-014**: GET /discounts ДОЛЖЕН возвращать только актуальные скидки (действующие на текущую дату).

**Скрипты заполнения данных (seed)**

- **FR-015**: `web/scripts/seed_stores.py` ДОЛЖЕН создавать форматы сети (Пятёрочка, Перекрёсток, Чижик) и по одному дефолтному магазину для каждого формата; скрипт идемпотентен (повторный запуск не дублирует данные).
- **FR-016**: `web/scripts/seed_discounts.py` ДОЛЖЕН сканировать JSONL-датасет (SEED_FILE_PATH), находить все уникальные пары (category_name, discount_pct) где discount_pct > 0, и создавать Discount-записи типа "акция" с link_type=category, scope=all, valid_to=NULL; скрипт идемпотентен.
- **FR-017**: `web/scripts/seed_receipts.py` ДОЛЖЕН читать JSONL-датасет (SEED_FILE_PATH) и импортировать до SEED_LIMIT пользователей (default=100, 0=все), создавая: LoyaltyCard (user_id → id, chain→store lookup, district_id→geo_cluster), Receipt (receipt_id как UUID-ключ), ReceiptItem (sku_id → product lookup; для on_promo позиций — поиск Discount по (category, discount_pct), discount_id=NULL если не найдено).
- **FR-018**: Порядок запуска seed-скриптов: `seed_products.py` → `seed_stores.py` → `seed_discounts.py` → `seed_receipts.py`; каждый скрипт настраивается только через env-переменные (SEED_FILE_PATH, SEED_LIMIT, DATABASE_URL).

### Key Entities

- **Receipt (Чек)**: покупка, привязанная к карте лояльности, магазину, дате; содержит позиции.
- **ReceiptItem (Позиция чека)**: товар × количество в чеке; хранит цену без скидки, цену к оплате, применённую скидку.
- **Store (Магазин)**: торговая точка с форматом сети и геокластером.
- **Discount (Скидка)**: процентная скидка с полиморфной привязкой (продукт / категория / бренд) и областью действия (all / by_format / by_store).
- **DiscountCalculationResult**: временная структура ответа на расчёт — не сохраняется в БД, только возвращается кассе.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Касса получает расчёт скидок по корзине из 20 товаров менее чем за 2 секунды.
- **SC-002**: Пользователь видит итоговую цифру экономии на главном экране за ≤2 действия от запуска приложения (требование Принципа II).
- **SC-003**: 100% позиций чека сохраняются с корректным base_price_at_purchase, paid_price и discounted_amount (верифицируется сравнением с product.current_price на момент покупки).
- **SC-004**: Выбор скидки соответствует best-price-wins для всех тестовых сценариев: продукт с 3+ конкурирующими скидками — выбирается с наибольшим discounted_amount.
- **SC-005**: Неавторизованные и пользовательские запросы на создание/изменение магазинов и скидок получают отказ в 100% случаев.

## Clarifications

### Session 2026-09-04

- Q: Что является уникальным ключом для обнаружения дублирующего чека? → A: Касса передаёт idempotency-key (UUID) в заголовке запроса; сервер возвращает тот же ответ без создания нового чека.
- Q: Что делать, если скидка истекла между расчётом и фиксацией чека? → A: Отклонить весь чек с ошибкой 422, перечислив проблемные позиции; касса перезапрашивает расчёт.
- Q: Как касса аутентифицируется для привилегированных запросов? → A: Статичный API-ключ в заголовке X-Terminal-Token (секрет из env); зафиксировано в ARCHITECTURE.md.
- Q: Что делать, если product_id из корзины не найден в каталоге? → A: Вернуть 422 с перечнем неизвестных product_id; ни расчёт, ни чек не создаются.
- Q: Как seed_receipts.py обрабатывает on_promo позиции (discount_pct > 0)? → A: Создавать синтетические Discount-записи для уникальных (category, discount_pct) пар через seed_discounts.py; seed_receipts.py ищет их и линкует через discount_id.

## Assumptions

- Касса аутентифицируется через статичный токен в заголовке `X-Terminal-Token` (секрет из env); на сервере — отдельный `TerminalTokenDep`. JWT не используется для кассы.
- `payment_card_uid` — необязательное поле для антифрода; в PoC передаётся, но не валидируется дополнительно.
- Расчёт скидок (шаг 4) и фиксация чека (шаг 5) — два отдельных запроса; сервер не гарантирует согласованность между ними (клиент передаёт discount_id из расчёта).
- Персональные скидки — те, чей discount_type.name = 'персональная'; остальные типы применяются ко всем.
- История покупок отображается в мобильном приложении; касса данные пользователя только читает, не отображает историю.
- Канал (channel) по умолчанию = 'offline' для кассовых запросов.
- Все даты обрабатываются в московском часовом поясе (UTC+3) согласно схеме.
- В рамках PoC скидки создаются через API или seeds; отдельный UI администратора не предусмотрен.
