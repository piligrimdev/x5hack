# Feature Specification: Product Catalog and Seed Script

**Feature Branch**: `004-product-catalog-seed`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "Реализуем работу с товарами. Проверь схему базы данных в context/schema. Возьми оттуда необходимые таблицы - категории, товары. Просмотр товаров доступен как мобильным юзерам, так и кассовому аппарату. Также необходимо будет создать скрипт, который будет заполнять данные в бд данными из json/jsonl файла."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр каталога товаров на мобильном устройстве (Priority: P1)

Пользователь открывает мобильное приложение и хочет посмотреть, какие товары есть в каталоге, чтобы понимать, на что могут распространяться скидки или персональные задания.

**Why this priority**: Это базовый просмотровый интерфейс, на котором строятся вся остальная логика (задания, скидки, рейтинг). Без него нельзя показать ни одну другую фичу.

**Independent Test**: Достаточно поднять бэкенд с загруженными тестовыми данными и выполнить запросы «получить список категорий» и «получить товары в категории» — оба должны вернуть данные.

**Acceptance Scenarios**:

1. **Given** в базе есть категории и товары, **When** мобильный клиент запрашивает список категорий, **Then** возвращается список категорий с id и названием каждой.
2. **Given** в базе есть товары категории «молочные продукты и яйца», **When** клиент запрашивает товары этой категории, **Then** возвращаются только товары данной категории с id, названием и актуальной ценой.
3. **Given** в базе нет товаров в категории, **When** клиент запрашивает товары этой категории, **Then** возвращается пустой список (не ошибка).

---

### User Story 2 - Поиск товара кассовым аппаратом по SKU (Priority: P1)

Кассовый аппарат сканирует штрихкод товара и должен получить актуальную цену и информацию о позиции для формирования чека.

**Why this priority**: Кассе нужен быстрый доступ к товару по внешнему идентификатору (SKU). Без этого невозможно имитировать процесс покупки и записать чек в базу.

**Independent Test**: Выполнить запрос «получить товар по SKU `sku_0000`» — должна вернуться карточка товара с ценой.

**Acceptance Scenarios**:

1. **Given** товар с SKU `sku_0042` есть в базе, **When** кассовый аппарат запрашивает товар по этому SKU, **Then** возвращается карточка товара: id, название, текущая цена, категория.
2. **Given** товара с указанным SKU нет в базе, **When** поступает запрос, **Then** возвращается понятный ответ «товар не найден» (404).

---

### User Story 3 - Импорт товаров из JSONL-файла (Priority: P2)

Оператор или скрипт загрузки данных читает файл формата JSONL (каждая строка — отдельный JSON-объект) и заполняет таблицы категорий и товаров.

**Why this priority**: Без наполнения базы данными нечего показывать на мобильном клиенте и кассе. Это операционный инструмент, который нужен один раз перед демо, но важен для воспроизводимости стенда.

**Independent Test**: Запустить скрипт с тестовым JSONL-файлом из 5 записей — в базе должны появиться соответствующие категории и товары; повторный запуск не должен создавать дубликаты.

**Acceptance Scenarios**:

1. **Given** JSONL-файл с 10 товарами из 3 разных категорий, **When** скрипт запускается, **Then** в базе появляются 3 категории и 10 товаров; каждый товар привязан к корректной категории.
2. **Given** скрипт уже выполнялся (данные есть в базе), **When** скрипт запускается повторно с тем же файлом, **Then** данные не дублируются (идемпотентный импорт).
3. **Given** в файле встречаются две записи с одинаковым `sku_id`, **When** скрипт обрабатывает их, **Then** в базе остаётся одна запись с данными из последней встреченной строки (UPSERT по sku_id).
4. **Given** строка в файле не содержит обязательных полей (`sku_id`, `item`, `category`, `regular_unit_price_rub`), **When** скрипт встречает её, **Then** строка пропускается с выводом предупреждения в лог; остальные строки обрабатываются.

---

### User Story 4 - Управление каталогом кассовым аппаратом (Priority: P3)

Кассовый аппарат (имитируемый клиент) может добавлять новые товары и категории, обновлять цены и удалять позиции из каталога через API.

**Why this priority**: Поддерживает актуальность каталога без полного перезапуска seed-скрипта; нужна как минимум как заглушка для полного контракта API.

**Independent Test**: Выполнить запрос «создать товар» с корректными данными — товар должен появиться в базе и быть доступен через GET-эндпоинты.

**Acceptance Scenarios**:

1. **Given** аутентифицированный клиент (JWT), **When** запрос на создание нового товара с sku_id, именем, ценой и категорией, **Then** товар появляется в базе и возвращается при GET-запросах.
2. **Given** товар существует, **When** запрос на обновление его цены, **Then** GET-запрос возвращает обновлённую цену.
3. **Given** товар существует, **When** запрос на удаление, **Then** GET-запрос по его SKU возвращает 404.

---

### Edge Cases

- Что происходит, когда в JSONL-файле встречается категория с незначительными опечатками (например, «молочные продуктыи яйца» без пробела)? Скрипт использует точное совпадение имени; оператор должен исправить файл вручную.
- Что если `regular_unit_price_rub` равно 0 или отрицательное? Товар пропускается, выводится предупреждение.
- Что если файл пустой или не является валидным JSONL? Скрипт завершается с понятным сообщением об ошибке, не изменяя состояние базы.
- Что если база данных недоступна при запуске скрипта? Скрипт завершается с ошибкой соединения до начала обработки данных.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST возвращать список всех категорий товаров с их идентификаторами и названиями.
- **FR-002**: Система MUST возвращать список товаров с фильтрацией по категории и поддержкой пагинации через query-параметры; каждый товар содержит id, название, актуальную цену и категорию. Ответ включает метаданные пагинации (текущая страница, общее количество страниц/записей).
- **FR-012**: Механизм пагинации MUST быть реализован как переиспользуемый компонент, применимый к любому эндпоинту со списком; управляется через query-параметры (например, `page` и `size`).
- **FR-003**: Система MUST позволять получить товар по его внешнему идентификатору SKU для кассового аппарата.
- **FR-004**: Система MUST возвращать 404 при запросе несуществующего SKU.
- **FR-005**: Читающие эндпоинты каталога (список категорий, список товаров, карточка товара по SKU) MUST требовать валидный JWT-токен; доступны любому аутентифицированному клиенту (мобильный пользователь и кассовый аппарат).
- **FR-011**: Пишущие эндпоинты каталога (создание, изменение, удаление товаров и категорий) MUST требовать валидный JWT-токен и зарезервированы для кассового аппарата. Ролевое разграничение на уровне JWT-middleware в рамках текущей архитектуры не реализуется; ограничение фиксируется как PoC-допущение.
- **FR-006**: Скрипт импорта MUST читать файл в формате JSONL (одна JSON-запись на строку) со структурой: `sku_id`, `category`, `item`, `regular_unit_price_rub`, `unit_cost_rub`, `gross_margin_rub`.
- **FR-007**: Скрипт импорта MUST создавать категории по названию, если они отсутствуют в базе; повторный запуск не должен создавать дублирующих категорий.
- **FR-008**: Скрипт импорта MUST работать по принципу UPSERT: если товар с данным `sku_id` уже есть в базе — обновить его название и цену; если нет — создать. Повторный запуск с тем же файлом не увеличивает количество записей.
- **FR-009**: SKU (`sku_id`) MUST храниться в таблице товаров как внешний идентификатор для обеспечения поиска кассой.
- **FR-010**: Скрипт импорта MUST пропускать строки с отсутствующими обязательными полями или невалидной ценой, выводя предупреждение по каждой такой строке.

### Key Entities

- **Category (Категория)**: Справочник категорий товаров. Ключевые атрибуты: уникальный id, уникальное название. Категории создаются при импорте по имени.
- **Product (Товар)**: Конкретная товарная позиция. Атрибуты: id, внешний SKU (уникальный), название, актуальная цена, принадлежность к категории. Бренд — опционален (не представлен в источнике данных).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Запрос списка категорий и списка товаров по категории выполняется за время, не воспринимаемое пользователем как задержка (мгновенный отклик при типичной нагрузке демо-стенда).
- **SC-002**: Скрипт импорта успешно загружает файл из 1000+ строк без ручного вмешательства оператора.
- **SC-003**: Повторный запуск скрипта импорта с тем же файлом не увеличивает количество записей в базе (идемпотентность проверяется счётчиком строк до и после).
- **SC-004**: 100% корректных строк из JSONL появляются в базе после первого запуска; строки с ошибками не прерывают обработку остальных.
- **SC-005**: Кассовый аппарат получает карточку товара по SKU за одно обращение к системе без дополнительных запросов.

## Clarifications

### Session 2026-09-04

- Q: Что должен делать скрипт импорта, когда товар с таким `sku_id` уже существует в базе — обновить его поля или пропустить строку? → A: UPSERT — обновить название и цену, если sku_id найден; создать, если нет.
- Q: Должны ли эндпоинты каталога требовать JWT-авторизацию, или они доступны без токена? → A: Читающие эндпоинты (GET) — требуют JWT, доступны любому авторизованному пользователю. Пишущие эндпоинты (создание/изменение/удаление) — требуют JWT, зарезервированы для кассового аппарата.
- Q: Должен ли эндпоинт списка товаров возвращать плоский список или поддерживать пагинацию? → A: Пагинация через query-параметры; механизм пагинации должен быть переиспользуемым (общий для всех подходящих эндпоинтов), предпочтительно через готовую библиотеку.

## Assumptions

- Поля `unit_cost_rub` и `gross_margin_rub` из JSONL не хранятся в базе данных на этапе PoC — они присутствуют в файле, но нужны только для аналитики и в MVP не используются. При необходимости это фиксируется в BACKLOG.
- Поле `brand_id` в таблице `product` допускает отсутствие значения для товаров, загруженных из JSONL (источник данных не содержит информации о бренде).
- Эндпоинты каталога доступны любому авторизованному пользователю без разделения ролей — кассовый аппарат и мобильный клиент используют один и тот же API.
- Путь к JSONL-файлу задаётся переменной окружения или конфигурационным файлом; аргументы командной строки не используются (согласно правилам скриптов проекта).
- Пишущие эндпоинты каталога входят в скоуп, но предназначены только для кассового аппарата (имитируемого клиента). Ролевое ограничение не реализуется на уровне JWT в данном PoC — текущая архитектура аутентификации не поддерживает роли.
- Актуальная цена товара (`current_price` в схеме) соответствует `regular_unit_price_rub` из JSONL.
- Для реализации пагинации предпочтительно использовать готовую библиотеку; механизм оформляется как единый переиспользуемый компонент, а не встраивается в каждый роут отдельно.
