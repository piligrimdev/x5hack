# Research: Реферальная программа

## R1 — Формат кода: 6 символов, смешанный регистр, сравнение точное

**Decision**: Код = ровно 6 символов из алфавита `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789` (62 символа). Генерация — `secrets.choice` по одному символу. Хранение и поиск — **как есть**, регистр значим (`AbC12x` ≠ `abc12x`). Невалидный ввод (длина ≠ 6 или символы вне алфавита) отклоняется 422 до любых записей.

**Rationale**: Явное уточнение к плану («6тизначный из цифр и латинских букв разного регистра»). Мобильный экран входа уже принимает 6 символов `[A-Za-z0-9]` и не складывает регистр (`login-view.tsx`, `CODE_LENGTH = 6`). Пространство 62⁶ ≈ 5.7×10¹⁰; коллизии на демо невозможны на практике. Уникальный индекс на колонке `code` + повтор генерации при `IntegrityError` (до 8 попыток).

**Alternatives considered**:
- Case-insensitive (верхний регистр при сохранении) — проще диктовать, но тогда «разный регистр» не часть идентичности и ломает уже написанный ввод.
- Только цифры или Crockford Base32 без `0/O/1/I` — удобнее голосом, но противоречит постановке.
- UUID / длинный токен — нельзя продиктовать на кассе/входе.

## R2 — Две таблицы: код и связка

**Decision**: `referral_code` — факт выдачи (inviter, строка кода, created_at). `referral_link` — появляется **только при активации**: invitee, снимки настроек, сроки окон, статус награды, FK на скидку и квалифицирующий чек.

**Rationale**: Неиспользованные коды не должны тащить пустые snapshot-поля. Список приглашений JOIN'ит код↔связку и считает статус (см. data-model). Соответствует сущностям спеки.

**Alternatives considered**:
- Одна широкая таблица на код — проще, но смешивает «выдан» и «активирован», сложнее уникальность «одна активная связка на invitee».
- Код как поле на `users` — один код на жизнь, противоречит FR-002/FR-004.

## R3 — Активация в той же транзакции, что регистрация/вход

**Decision**: `PhoneRequest.referral_code: str | None`. `AuthService.register/login` вызывают `ReferralService.activate(...)` в той же сессии. `UserRepository.create` сейчас делает `session.commit()` — для этой фичи добавляется путь **flush без commit** (`create` / новый `add`), чтобы невалидный код не оставлял пользователя (FR-009).

Порядок register с кодом:
1. Нормализовать телефон, проверить уникальность.
2. `SELECT … FOR UPDATE` по коду; отказ, если нет / уже есть link / свой (для login).
3. Создать user + loyalty card (flush).
4. Создать `referral_link` + персональную скидку.
5. Один `commit`, затем выдать JWT.

Login с кодом: найти user → если кода нет, выдать JWT как сейчас → если код есть, проверить 180 дней / активную связку / не свой код → activate → commit → JWT. При отказе реактивации сессия **не** выдаётся (FR-010).

**Rationale**: FR-007/FR-009 требуют «всё или ничего». Ранний commit в репозитории — известный долг 003; чинить точечно, не переписывая все вызовы.

**Alternatives considered**:
- Сначала создать user, потом активировать — при плохом коде остаётся аккаунт без скидки, нарушает FR-009.
- Отдельный `POST /referrals/activate` после логина — противоречит спеке («только при регистрации или входе»).

## R4 — Реактивация = 180 суток без чеков

**Decision**: Запрос `EXISTS` по `receipts` с `loyalty_card_id = user.id` и `purchase_date >= now(Europe/Moscow) - 180 days`. Есть хотя бы один чек → 409, код не гасится, JWT нет. Нет чеков (или все старше) → активация как у новичка.

«Активная связка» блокирует второй код: есть `referral_link` этого invitee, у которой `now < purchase_window_until` **или** `now < discount_valid_to`, и статус не терминальный. После закрытия обоих окон повторный код — только через этот же 180-дневный вход (FR-013).

**Rationale**: Спека фиксирует 180 суток и Europe/Moscow. Чек — уже источник истины покупок (005). Не вводим отдельный «статус сети» на user.

**Alternatives considered**:
- Считать «таймаут» как истечение JWT — отвергнуто спекой.
- Календарные 6 месяцев (`date - relativedelta`) — сложнее границ; 180 дней однозначнее.

## R5 — Ошибки: не 403 на логине с кодом

**Decision**: Тексты в `{"detail": "..."}` (как FR-011 спеки 003). Коды:

| Ситуация | HTTP | detail (смысл) |
|----------|------|----------------|
| Код не 6 символов / не `[A-Za-z0-9]` | 422 | Некорректный формат кода |
| Кода нет | 409 | Код не найден |
| Код уже активирован | 409 | Код уже использован |
| Свой код | 409 | Нельзя пригласить себя |
| Уже есть активная связка | 409 | Реферальная скидка уже действует |
| Есть покупки за 180 дней | 409 | Реактивация недоступна: недавно были покупки. Войдите без кода |
| Логин, пользователя нет | 404 | как сейчас, код аккаунт не создаёт |
| Телефон занят (register) | 409 | как сейчас; код проверяется **до** создания |

**Rationale**: Мобильный `loginHint` трактует **403 как «номер не зарегистрирован»**. 403 для «недавние покупки» сломает UX. 409 = конфликт бизнес-правила, 422 = форма.

**Alternatives considered**: 403 для реактивации — конфликтует с клиентом. Problem+json — лишний формат.

## R6 — Скидка приглашённого = существующий Discount

**Decision**: При активации создать `Discount`: `discount_types.name = 'персональная'`, `discount_link_types.name = 'all'`, `entity_id NULL`, `value_type = 'percent'`, `value = X` (снимок), `loyalty_card_id = invitee`, `scope = 'all'`, `valid_from = now`, `valid_to = now + 7×24h`. Сид `'all'` в `discount_link_types` добавить миграцией: калькулятор (`find_applicable_for_cart`) уже ищет этот link_type, но в сиде 005 его нет (только product/category/brand).

Best-price-wins не меняем (`DiscountCalculatorService`).

**Rationale**: FR-016/FR-017. Не плодим отдельный «реферальный процент» в калькуляторе чека.

**Alternatives considered**:
- Скидка на итог чека после баллов — расходится с 005/007 (сначала товары, потом баллы).
- Процент только на первую покупку — спека говорит «все покупки недели».

## R7 — Награда приглашающему в транзакции чека, не в Celery

**Decision**: `ReceiptService.create_receipt` после успешного insert нового чека (`is_new`) и до `session.commit()` вызывает `ReferralService.award_on_receipt(session, invitee_id, receipt_id)`. Условия: есть связка invitee со статусом `awaiting_purchase`, `now <= purchase_window_until`. Тогда: купоны + кешбек по снимку, статус `rewarded`, `qualifying_receipt_id = receipt.id`. Идемпотентность: UNIQUE на `referral_link.qualifying_receipt_id` и частичные UNIQUE на tx `related_referral_link_id`.

Повторная обработка того же чека (`is_new=False`) награду не вызывает. Покупка после окна не меняет статус (он станет `expired` лениво при чтении списка, либо останется `awaiting_purchase` с прошедшим `purchase_window_until` — API отдаёт `expired`).

`process_receipt` (Celery) **не** начисляет реферал: задача fire-and-forget и может не выполниться (уже глотает ошибки Redis).

**Rationale**: FR-022 — атомарно с квалифицирующей покупкой.

**Alternatives considered**: Celery — проще врезать рядом с заданиями, но нарушает «награда вместе с чеком» и даёт окно двойного начисления при ретрае.

## R8 — Купоны и баллы: новый тип / FK, без rollback

**Decision**:
- `coupon_transaction.type` += `'referral'`; колонка `related_referral_link_id`; UNIQUE where type=referral.
- `points_transaction` += `related_referral_link_id`; UNIQUE earn по этой колонке.
- `CouponService.award_for_referral`, `PointsService.award_for_referral` — формула баллов **как в живом коде** (`round(rub * rate / 10) * 10`), не «as-is» из старой спеки 007 (тот же вывод, что R6 колеса).
- При `IntegrityError` **не** вызывать `session.rollback()` (ловушка `insert_earn` из 009).

Нулевые снимки (0 купонов / 0 ₽) не пишут строку леджера (FR-025).

**Rationale**: FR-023/FR-024. Отдельный кошелёк сломал бы единую экономию (принцип I).

**Alternatives considered**: Переиспользовать `task_complete` / `related_task_id` — лжёт в истории. Начислять баллы без FK — нет идемпотентности.

## R9 — Настройки из env, снимок в связке

**Decision**: Читать при **активации** (не при выдаче кода и не при награде):

| Env | Default | Допустимо |
|-----|---------|-----------|
| `REFERRAL_INVITEE_DISCOUNT_PERCENT` | `10` | 0–100, число |
| `REFERRAL_INVITER_COUPONS` | `2` | целое ≥ 0 |
| `REFERRAL_INVITER_CASHBACK_RUB` | `50` | целое ≥ 0 |

Невалидное значение — `RuntimeError` при старте/чтении (как `FORTUNE_WHEEL_WEEKLY_COUPONS`). 180 дней и 7 суток — константы продукта в коде, не env (спека их зафиксировала словами, не «настройками размера»).

Хелперы в `core/referral.py`, рядом с wiring сервиса.

**Rationale**: FR-015/FR-021/FR-027. Смена env после активации не должна менять уже обещанную связку.

**Alternatives considered**: Таблица настроек как `points_settings` — избыточно для трёх чисел хакатона.

## R10 — Генерация и список: REST `/referrals`

**Decision**:
- `POST /referrals` — выдать новый код (Bearer, держатель карты = любой авторизованный user; карта создаётся при register).
- `GET /referrals` — список своих кодов от новых к старым + вычисляемый статус.

Статусы ответа (не колонка кода): `issued` | `awaiting_purchase` | `rewarded` | `expired`.

**Rationale**: FR-001/FR-028. Отдельный ресурс проще, чем раздувать `GET /me`.

**Alternatives considered**: Возвращать код в `GET /me` — нет истории. GraphQL — нет в проекте.

## R11 — Мобильный вход уже готов; экран приглашения — 1 тап с главной

**Decision**: `login-view.tsx` / `apiLogin` / `apiRegister` уже шлют `referral_code`. Доработать хинты: для 409/422 показывать `ApiError.detail`, не «номер не зарегистрирован». Новый экран `referral-view.tsx` + хук `useReferrals`. Вход: QuickAction на `home-view` («Пригласить») → `index.tsx` screen `'referral'`. Копирование — `expo-clipboard` (`npx expo install`). Отправка — `Share.share` из `react-native` (без eject).

**Rationale**: FR-001, принцип II, Mobile Technical Standards. Системный share есть на iOS/Android без нативных пакетов.

**Alternatives considered**:
- Профиль (вкладка есть, экрана нет) — дальше от «1 действие с главной».
- Deep link / SMS — вне скоупа, нет push/SMS.

## R12 — Юнит-экономика демо (принцип IV)

**Decision**: Для демо считать стоимость одной сработавшей связки как:

`X% × сумма покупок invitee за 7 дней + REFERRAL_INVITER_CASHBACK_RUB + REFERRAL_INVITER_COUPONS × ожидаемая стоимость спина (~39 ₽ по research 009)`.

При дефолтах и одном чеке 800 ₽: `80 + 50 + 2×39 ≈ 208 ₽`. Показывать жюри как «пилот» нельзя, пока владелец экономики не сравнит это с маржой вернувшегося чека (H4 / принцип IV). Антифрод карт — вне скоупа (как в конституции).

**Rationale**: Честная калибровка env без блокировки реализации.

**Alternatives considered**: Не фиксировать оценку — тогда IV формально «не применимо», что хуже для демо.
