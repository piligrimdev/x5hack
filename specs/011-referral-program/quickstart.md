# Quickstart: Реферальная программа

## Предусловия

```bash
cd web
docker compose up -d postgres
poetry run alembic upgrade head
```

В `.env`:

```bash
REFERRAL_INVITEE_DISCOUNT_PERCENT=10
REFERRAL_INVITER_COUPONS=2
REFERRAL_INVITER_CASHBACK_RUB=50
JWT_SECRET_KEY=...
TERMINAL_TOKEN=...
```

Базовый URL: `http://localhost:8000`.  
Контракты: [contracts/api-contracts.md](contracts/api-contracts.md). Модель: [data-model.md](data-model.md).

Нужны два телефона (приглашающий A, приглашённый B) и возможность зафиксировать чек кассовым токеном (как в quickstart 005).

---

## Сценарий 1: Выдать два разных кода

Зарегистрировать A без кода, сохранить `A_TOKEN`.

```bash
curl -X POST http://localhost:8000/referrals \
  -H "Authorization: Bearer $A_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{}'
```

Ожидание: 201, `code` длиной 6 из `[A-Za-z0-9]`, `status=issued`. Повторить запрос — другой `code`, первый по `GET /referrals` остаётся `issued`.

Без токена: 401.

**Требования**: FR-001, FR-002, FR-004, FR-031, SC-001, SC-002.

---

## Сценарий 2: Регистрация с кодом

```bash
curl -X POST http://localhost:8000/register \
  -H "Content-Type: application/json" \
  -d '{"phone":"+79000000002","referral_code":"<CODE_FROM_A>"}'
```

Ожидание: 200, токены B. Повтор той же регистрации — 409 (телефон). Повтор **другого** нового телефона с тем же кодом — 409 (код использован).

Регистрация с `AbC12x` vs `abc12x`: это разные коды; несуществующий регистровый вариант — 409 «не найден».

Регистрация с `"referral_code":"12"` — 422, пользователь не создан (повтор register без кода на тот же номер не должен дать 409 «уже есть», если аккаунт не появился).

**Требования**: FR-007, FR-009, FR-031, SC-003, SC-009.

---

## Сценарий 3: Реактивация и отказ при недавней покупке

Пользователь C уже есть. Если у него есть чек младше 180 дней:

```bash
curl -i -X POST http://localhost:8000/login \
  -H "Content-Type: application/json" \
  -d '{"phone":"<C_PHONE>","referral_code":"<FRESH_CODE>"}'
```

Ожидание: 409, текст про недавние покупки, токена нет, код остаётся `issued`. Тот же логин **без** кода — 200.

Пользователь D без чеков 180 дней + свежий код — 200, скидка стартует, код `awaiting_purchase`.

Логин несуществующего номера с кодом — 404, код не гасится.

**Требования**: FR-008, FR-010, FR-011, SC-004, SC-005.

---

## Сценарий 4: Скидка приглашённого на расчёте чека

Пока окно 7 суток открыто, `POST /receipts/calculate` с картой B: в позициях видна персональная скидка 10% (если не проиграла более выгодной), `total_saved` вырос.

После сдвига часов за `discount_valid_to` (в тесте — подмена часов) та же корзина считается без этой скидки.

**Требования**: FR-014, FR-016, FR-017, FR-018, SC-007.

---

## Сценарий 5: Награда приглашающему после покупки

Зафиксировать новый чек B (`POST /receipts`, `X-Idempotency-Key`) внутри окна.

Ожидание: у A баланс купонов +2, в истории купонов `type=referral`; на счёте баллов A начисление, связанное со связкой; `GET /referrals` у A — `status=rewarded`.

Повтор того же idempotency-key — награда не удваивается. Второй новый чек B в том же окне — тоже без второй награды.

Чек B после истечения окна (отдельная связка без покупки 7 суток) — A без наград, статус `expired`.

**Требования**: FR-019–FR-026, SC-006.

---

## Сценарий 6: Самоприглашение

A логинится со своим же кодом — 409, код остаётся `issued`.

**Требования**: FR-005, SC-009.

---

## Сценарий 7: Мобильный контур (ручной)

1. Главная → «Пригласить» (1 тап) → виден код, «Скопировать» / системный share.
2. Второй девайс: экран входа, 6 сегментов, вставить код как есть (регистр), регистрация.
3. На первом девайсе список меняет статус после покупки второго.

Ожидание: код совпадает с `POST /referrals`; 409 с сервера показывается текстом `detail`, а не «номер не зарегистрирован».

**Требования**: FR-001, FR-028, FR-030, SC-001, SC-008.

## Негатив настроек

`REFERRAL_INVITEE_DISCOUNT_PERCENT=101` или отрицательные купоны — процесс не должен раздавать связки с невалидными снимками (падение при чтении env / отказ активации).
