Все пункты закрыты. Открытых NEEDS CLARIFICATION нет.

## R1 — Считать на чтении, без снэпшотов

**Decision**: `GET /leaderboard` считает рейтинг в запросе. Новых таблиц, materialized view и Celery `update_rating` нет.

**Rationale**: Спека требует актуальный состав после новой покупки (окно 20 чеков сдвигается). В PoC сотни пользователей и тысячи чеков; одно оконное чтение + агрегация месяца укладываются в SC-006 (< 3 с). `ARCHITECTURE.md` описывал предрасчёт по `geo_cluster` — это бэклог районного рейтинга, не эта фича.

**Alternatives considered**:
- Таблица `user_home_store` + джоб на каждый чек — актуальность ценой миграций и гонок.
- Materialized view по району — другая единица агрегации (конституция V / бэклог), не магазин.

## R2 — Два запроса в репозитории, ранг в сервисе

**Decision**:

1. `list_recent_store_votes(session, window=20)` — для каждого `loyalty_card_id` последние 20 чеков с непустым `store_id` (`ROW_NUMBER() … ORDER BY purchase_date DESC, id DESC`), затем `COUNT` и `MAX(purchase_date)` по магазину.
2. `list_monthly_savings(session, month_start, month_end)` — на пользователя: `SUM(discounted_amount × qty) + SUM(cashback_applied_rub)` и `SUM(base_price × qty)` по чекам месяца.

`LeaderboardService` выбирает home store (мода + тай-брейк), фильтрует когорту, округляет процент, считает competition-ранг (1, 2, 2, 4).

**Rationale**: RSI: репозиторий не ранжирует. Сервис тестируется на фикстурах без SQL. Окно и месяц — параметры, не магия в SQL.

**Alternatives considered**: один SQL с `RANK()` — сложнее тестировать тай-брейк и анонимизацию; N+1 `list_by_loyalty_card(size=20)` на каждого кандидата — неприемлемо.

## R3 — Home store: мода окна 20, стабильный тай-брейк

**Decision**: Последние 20 чеков пользователя с `store_id IS NOT NULL`, порядок `purchase_date DESC, id DESC`. Home store = `store_id` с максимальным числом вхождений. Ничья по частоте → магазин с более поздней покупкой в окне. Ничья по времени → меньший `store_id` (стабильность SC-004).

Чеки без магазина не голосуют. Если после фильтра окно пустое — статуса `no_home_store`.

Константа `HOME_STORE_WINDOW = 20` в сервисе.

**Rationale**: FR-004–FR-006 плюс «один и тот же выбор при повторных запросах». `id` как второй ключ сортировки закрывает одинаковый `purchase_date`.

**Alternatives considered**: только последняя покупка — отвергнуто спекой; все чеки за всё время — слишком инерционно.

---

## R4 — Когорта = тот же home store, не «хоть раз был в магазине»

**Decision**: Участник рейтинга — пользователь, у которого home store (то же правило 20) совпал с магазином зрителя **и** за текущий месяц `total_base > 0`.

**Rationale**: FR-007, FR-008, FR-011. Иначе в топ попадут гости, для которых этот магазин не «свой».

**Alternatives considered**: все, у кого есть чек в магазине А за месяц — проще SQL, ломает спеку.

## R5 — Процент = формула Аппи, месяц Europe/Moscow

**Decision**:

```
savings_percent = round((discount_saved + cashback_applied_rub) / total_base * 100)
```

`discount_saved = SUM(discounted_amount × qty)`, знаменатель — все магазины пользователя за месяц. Если `total_base <= 0` — пользователь не в таблице мест. Значение режется в диапазон 0…100 (кешбек теоретически может раздуть числитель).

Границы месяца: `[1-е 00:00, 1-е следующего)` в `ZoneInfo("Europe/Moscow")`, тот же пояс, что `WHEEL_TZ`. Вынести `PRODUCT_TZ` в `webx5/core/timezone.py` и переиспользовать из колеса — в этой фиче достаточно локальной константы `LEADERBOARD_TZ`; общий рефактор колеса не обязателен.

Клиент **не** пересчитывает процент: рисует поля ответа. Блок Аппи по-прежнему агрегирует `/receipts` в TZ устройства; на демо в Москве они совпадают.

**Rationale**: FR-009, FR-010, допущения спеки. Сервер — источник истины рейтинга (FR-002).

**Alternatives considered**: процент только по чекам «своего» магазина — разойдётся с «от всех покупок» на Аппи; all-time процент — другой период, чем тап по месячной статистике.

## R6 — Эндпоинт `GET /leaderboard`, пустые состояния в 200

**Decision**: Один ресурс `GET /leaderboard`. Без токена — 401. С токеном всегда 200 и дискриминатор `status`:

| `status` | Когда | `store` | `me` | `entries` |
|----------|--------|---------|------|-----------|
| `no_home_store` | нет чеков / нет store_id | `null` | `null` | `[]` |
| `ready` | home store есть | заполнен | объект или `null` | топ-10 |

`me is null` при `ready` = в этом месяце нет покупок с `total_base > 0` (FR-015, US4.2).  
`solo: true` если `participant_count == 1` и зритель в таблице.

Не 404: клиенту нужны тексты пустых состояний, это не «нет ресурса».

**Rationale**: FR-002, FR-003, FR-019. Тот же стиль, что `GET /wheel` (персональный снимок).

**Alternatives considered**: `GET /receipts/leaderboard` — прячет механику рейтинга; 404 без покупок — клиент не отличит «нет магазина» от «сломан URL».

## R7 — Топ-10 в `entries`, зритель отдельно в `me`

**Decision**: `entries` — не больше 10 строк, отсортированы по проценту убыв., при равном проценте — стабильно по `loyalty_card_id` (только порядок строк, не место). Если зритель в десятке, у его строки `is_me: true`. Объект `me` всегда дублирует место/процент, если он в таблице. `me.in_top` говорит клиенту, нужна ли отдельная строка «Вы» под списком.

**Rationale**: FR-016. Клиент не вычисляет ранг.

**Alternatives considered**: отдать всех участников — лишний трафик и риск деанонимизации масштабом; только перцентиль без списка — слабее «лидерборд».

---

## R8 — Анонимные подписи без UUID и ПД

**Decision**: Чужая строка: `label = "Покупатель {code}"`, где `code` — целое `100…999` из `sha256(loyalty_card_id)[:8]` как int `% 900 + 100`. В JSON нет `user_id`, телефона, адреса. У зрителя в UI подпись «Вы»; в API достаточно `is_me`.

Название магазина: `"{format_name}, {geo_cluster}"` (как в списке чеков). `address` не отдаём.

**Rationale**: FR-017, FR-018, принцип V. Стабильный код узнаваем между открытиями, не является прямым идентификатором.

**Alternatives considered**: ФИО из профиля — запрещено; сырой UUID / last-4 UUID — прямой идентификатор; порядковый номер в топе — прыгает при смене мест.

## R9 — Competition rank, рубли не тай-брейк

**Decision**: Сортировка только по `savings_percent` DESC. Одинаковый округлённый процент → одно место, следующий номер пропускается (1, 2, 2, 4).  
`beats_percent = floor(count(percent < me.percent) / M * 100)`. При `M == 1` → 0.

**Rationale**: FR-012, FR-013, FR-015.

**Alternatives considered**: dense rank (1, 2, 2, 3) — не то, что в спеке; тай-брейк рублями — явно запрещён.

## R10 — Мобильный вход: state-экран, как колесо

**Decision**: Навигация в `x5mobile/src/app/index.tsx` — `Screen` + `'leaderboard'`. Тап по `chartCard` на Аппи → `onOpenLeaderboard`. Экран `SavingsLeaderboardView` + хук `useSavingsLeaderboard` (`apiFetch('/leaderboard', token)`). Стили — локальные константы Аппи (`#138F3E` и т.д.).

Чтобы выполнить US1.4 (скролл Аппи после «назад»), Аппи **не размонтировать**: рендерить его скрытым, пока `screen === 'leaderboard'`, лидерборд сверху. Таб «Аппи» остаётся активным, как для колеса.

**Rationale**: FR-001. В приложении нет Expo Router stack; Modal — для пикеров, не для экрана механики.

**Alternatives considered**: Modal внутри `AppiView` — нет единого паттерна «назад»; размонтировать Аппи как колесо — проще, но ломает US1.4.

## R11 — Индексы и миграции

**Decision**: Новых таблиц нет. Существующих `ix_receipts_loyalty_card_id`, `ix_receipts_store_id`, `ix_receipts_purchase_date` достаточно для PoC. Опциональный составной `(loyalty_card_id, purchase_date DESC)` не блокирует план; не добавляем в обязательный скоуп.

**Rationale**: Меньше поверхность. Если окно по всем пользователям станет медленным — индекс или кэш, не сейчас.

---

## R12 — Принцип I: процент vs «рейтинг в рублях»

**Decision**: Место выражает **долю сэкономленных рублей**, не очки активности. Абсолютные рубли в сортировке запрещены спекой (крупный чек иначе всегда выигрывает). В UI процент рядом с уже видимой рублёвой сводкой на Аппи.

**Rationale**: Конституция I требует экономию в рублях, не абстрактные баллы. Нормированная доля — та же экономия. Это не новая игровая валюта.

---

## R13 — Принцип V: магазин вместо дома/района

**Decision**: Единица когорты — `stores.id` (явный запрос + спека). `geo_cluster` уже есть у магазина и входит в отображаемое имя, но группировка не та. ПД в строках нет (R8). Районный рейтинг из бэклога не реализуется.

**Rationale**: Спека важнее общего бэклога. Отклонение от «дом/район» фиксируется в Complexity Tracking плана, не блокирует PoC.

---

## R14 — Auth и карта лояльности

**Decision**: `CurrentUserUUID`. Анонимные чеки (`loyalty_card_id IS NULL`) не входят ни в окно 20, ни в месяц. Отдельной проверки «есть ли карта» сверх JWT не нужно: в этой системе `users.id` и есть карта.

**Rationale**: Как `/receipts/economy` и `/wheel`.
