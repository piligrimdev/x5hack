## Clarifications

### Session 2026-09-06

- Q: Как кассовый аппарат авторизуется для доступа к CRUD-эндпоинтам вайбов? → A: Статический API-ключ (уже реализован в проекте).
- Q: При применении награды-подарок система добавляет бесплатную позицию или делает скидку на существующую? → A: Делает скидку на существующую позицию в корзине (товар должен уже быть добавлен пользователем).
- Q: Что делать с полями vibe_category/vibe_month при переходе на VibeType? → A: Создать VibeType-записи из существующих VIBE_CATEGORIES, смигрировать пользователей по совпадению имени вайба.
- Q: При category-уровне подарка и нескольких подходящих товарах в корзине — какой получает скидку? → A: Самый дешёвый подходящий товар.
- Q: Товар, подходящий под несколько пунктов задания одновременно, засчитывается в оба? → A: Да — засчитывается во все применимые пункты параллельно.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Составное задание: выполнить все пункты (Priority: P1)

Пользователь видит задание «Собери всё для салата Цезарь», которое включает несколько пунктов: купить куриное филе 2 шт. и купить яйца 1 шт. По мере добавления этих товаров в корзину и совершения покупок прогресс каждого пункта обновляется независимо. Задание считается выполненным только тогда, когда все пункты закрыты.

**Why this priority**: Это ключевое расширение механики заданий — без него составные задания невозможны в принципе.

**Independent Test**: Можно полностью протестировать, создав задание с двумя пунктами и проверив, что оно не закрывается при выполнении только одного из них.

**Acceptance Scenarios**:

1. **Given** задание содержит два пункта (куриное филе 2 шт., яйца 1 шт.), **When** пользователь покупает только куриное филе 2 шт., **Then** задание НЕ считается выполненным, а прогресс по пункту «куриное филе» отображается как 100%, по «яйца» — 0%.
2. **Given** пользователь купил оба пункта в нужных количествах, **When** обрабатывается чек, **Then** задание переходит в статус «выполнено» и начисляется награда.
3. **Given** задание содержит три пункта, **When** пользователь выполнил два из трёх, **Then** общий прогресс отображается пропорционально выполненным пунктам.
4. **Given** пункт задания по категории «молочные продукты» и пункт по SKU «молоко», **When** пользователь покупает 1 молоко, **Then** прогресс засчитывается в оба пункта параллельно и независимо.

### User Story 2 — Награда-подарок: применить при расчёте (Priority: P1)

Пользователь выполнил задание с наградой-подарком («Купи 5 шоколадок — 6-я бесплатно»). При следующей покупке подарок доступен к применению: если в корзине есть подходящий товар, система автоматически снижает цену одной его единицы до нуля.

**Why this priority**: Без применения подарка при расчёте механика не даёт видимого результата пользователю, что нарушает Принцип I конституции (экономия как единая метрика).

**Independent Test**: Создать задание с наградой-подарком, выполнить его, добавить в корзину нужный товар — подарок должен отобразиться как скидка с нулевой ценой.

**Acceptance Scenarios**:

1. **Given** у пользователя есть активная награда «1 шоколадка бесплатно» и шоколадка есть в корзине, **When** система рассчитывает корзину, **Then** цена одной шоколадки обнуляется, итоговая сумма уменьшается на её стоимость.
2. **Given** у пользователя есть награда-подарок и товар присутствует в чеке, **When** создаётся чек через API, **Then** paid_price = 0 для одной единицы этого товара.
3. **Given** у пользователя нет подходящего товара в корзине, **When** он смотрит состав корзины, **Then** подарок не применяется, но остаётся в списке доступных наград.
4. **Given** у пользователя есть неиспользованная награда-подарок с истёкшим сроком, **When** он открывает корзину, **Then** подарок недоступен к применению и отмечен как просроченный.
5. **Given** награда-подарок привязана к категории и в корзине несколько товаров из этой категории, **When** система рассчитывает корзину, **Then** скидка применяется к самому дешёвому из подходящих товаров.

### User Story 3 — Вайб: пользователь выбирает направление рекомендаций (Priority: P2)

Пользователь видит список доступных вайбов (например, «Здоровое питание», «Экономия», «Быстрый ужин»). Он выбирает один — и последующие задания и подсказки корзины начинают учитывать выбранное направление. Он может сменить вайб в любой момент или отказаться от него, вернувшись к обычной персонализации.

**Why this priority**: Функционал задаёт персональный контекст для ИИ-рекомендаций; без данных, хранимых в API, это невозможно реализовать.

**Independent Test**: Установить вайб через API, получить список активных заданий — хотя бы один слот должен содержать задание, соответствующее категориям вайба.

**Acceptance Scenarios**:

1. **Given** пользователь не выбрал вайб, **When** он запрашивает список доступных вайбов, **Then** список содержит все активные вайбы с названием и описанием.
2. **Given** доступные вайбы существуют, **When** пользователь выбирает вайб, **Then** за ним закрепляется выбранный вайб и генерация заданий начинает его учитывать.
3. **Given** у пользователя закреплён вайб, **When** он выбирает другой вайб, **Then** предыдущий снимается, закрепляется новый.
4. **Given** у пользователя закреплён вайб, **When** он отказывается от вайба, **Then** поле вайба очищается, рекомендации возвращаются к обычной персонализации без тематического ограничения.

---

### User Story 4 — Кассовый аппарат управляет типами вайба (Priority: P2)

Оператор через интерфейс «кассового аппарата» (POS-система) создаёт новый тип вайба: вводит название, описание и контекст (текст, передаваемый ИИ при генерации рекомендаций). Существующие типы можно редактировать или удалять. При удалении активного вайба пользователей их вайб сбрасывается автоматически. Доступ к этим операциям защищён статическим API-ключом.

**Why this priority**: Без CRUD-управления типами вайба пользователи не смогут их выбирать.

**Independent Test**: Создать вайб через API кассового аппарата с валидным API-ключом, убедиться, что он появился в списке для пользователей.

**Acceptance Scenarios**:

1. **Given** кассовый аппарат передаёт валидный API-ключ, **When** он создаёт новый вайб с названием, описанием и контекстом, **Then** вайб появляется в общем списке и доступен пользователям для выбора.
2. **Given** существующий вайб, **When** кассовый аппарат изменяет его описание или контекст, **Then** изменения применяются немедленно; уже выбравшие этот вайб пользователи получают обновлённый контекст при следующей генерации.
3. **Given** вайб выбран одним или несколькими пользователями, **When** кассовый аппарат удаляет этот вайб, **Then** у всех затронутых пользователей вайб сбрасывается (становится пустым).
4. **Given** кассовый аппарат пытается создать вайб с уже существующим названием, **Then** операция отклоняется с ошибкой конфликта.
5. **Given** запрос к CRUD-эндпоинтам вайба без API-ключа или с невалидным ключом, **Then** запрос отклоняется с ошибкой авторизации.

---

### Edge Cases

- Что происходит, если в составном задании один из пунктов ссылается на товар, которого нет в каталоге?
- Что если пользователь добавляет в корзину 0 единиц подходящего для подарка товара (пустая корзина)?
- Что если пользователь пытается применить один и тот же подарок дважды?
- Что если в задании есть пункт по категории — и в одном чеке несколько товаров из этой категории частично закрывают пункт?
- Что если кассовый аппарат удаляет вайб в момент генерации задания для пользователя, у которого он был выбран?

## Requirements *(mandatory)*

### Functional Requirements

#### Составные задания

- **FR-001**: Задание ДОЛЖНО поддерживать один или несколько независимых пунктов выполнения, каждый из которых задаёт тип критерия (товар или категория), идентификатор сущности и целевое количество.
- **FR-002**: Прогресс по каждому пункту задания ДОЛЖЕН отслеживаться и обновляться независимо при каждом чеке.
- **FR-003**: Задание ДОЛЖНО переходить в статус «выполнено» только тогда, когда все его пункты достигли целевого значения.
- **FR-004**: API ДОЛЖЕН возвращать прогресс по каждому пункту задания отдельно, а не единым агрегированным числом.
- **FR-005**: Существующие задания с одним пунктом ДОЛЖНЫ продолжать работать без изменений.
- **FR-006**: Если купленный товар подходит под несколько пунктов задания одновременно (например, пункт по SKU и пункт по категории), он ДОЛЖЕН засчитываться в прогресс всех применимых пунктов параллельно.

#### Типы наград

- **FR-007**: Система ДОЛЖНА поддерживать как минимум два типа наград: кешбэк (начисление баллов) и подарок (скидка на существующий товар в корзине до нулевой цены).
- **FR-008**: Награда-подарок ДОЛЖНА быть привязана к конкретному товару (SKU) или категории и хранить количество бесплатных единиц.
- **FR-009**: При формировании предварительного расчёта корзины система ДОЛЖНА применять подарок как скидку на существующую позицию, если подходящий товар есть в корзине.
- **FR-010**: Если награда-подарок привязана к категории и в корзине несколько подходящих товаров, скидка применяется к самому дешёвому из них.
- **FR-011**: При создании чека система ДОЛЖНА применять активные награды-подарки пользователя, если соответствующие товары присутствуют в чеке, и фиксировать paid_price = 0 для подарочных позиций.
- **FR-012**: Использованная награда-подарок ДОЛЖНА быть помечена как применённая и недоступна для повторного использования.
- **FR-013**: API ДОЛЖЕН возвращать список активных наград пользователя с указанием типа, описания и применимости к текущей корзине.

#### Вайб

- **FR-014**: Система ДОЛЖНА хранить каталог типов вайба, каждый из которых содержит название (уникальное), описание и LLM-контекст.
- **FR-015**: Кассовый аппарат ДОЛЖЕН иметь возможность создавать, редактировать и удалять типы вайба через отдельный защищённый API с аутентификацией по статическому API-ключу.
- **FR-016**: Пользователь ДОЛЖЕН иметь возможность выбрать один из доступных вайбов, сменить его или сбросить (отказаться от вайба).
- **FR-017**: При удалении типа вайба система ДОЛЖНА автоматически сбрасывать выбранный вайб у всех пользователей, у которых он был активен.
- **FR-018**: При генерации задания для пользователя с активным вайбом система ДОЛЖНА передавать LLM-контекст вайба в промпт, ограничивая выбор категорий теми, что указаны в вайбе.
- **FR-019**: Рекомендации корзины ДОЛЖНЫ учитывать LLM-контекст активного вайба пользователя при формировании ответа ассистента.
- **FR-020**: Пользователь без выбранного вайба ДОЛЖЕН получать рекомендации на основе обычной персонализации без тематического ограничения.

### Key Entities

- **TaskCriterion (пункт задания)**: Один независимый пункт составного задания. Атрибуты: тип критерия (товар/категория), идентификатор целевой сущности, целевое количество, текущий прогресс. Принадлежит одному заданию; задание может иметь несколько пунктов. Пункты одного задания проверяются независимо — выполнение одного не блокирует зачёт в другой.
- **Reward (награда)**: Начисляемое вознаграждение за выполнение задания. Атрибуты: тип (кешбэк / подарок), статус (активна / использована / просрочена), привязка к заданию. Для подарка — дополнительно: идентификатор товара (SKU) или категории, количество бесплатных единиц.
- **VibeType (тип вайба)**: Управляемая кассовым аппаратом сущность. Атрибуты: название (уникальное), описание для пользователя, контекст для LLM. Один тип вайба может быть выбран многими пользователями.
- **User (пользователь)**: Расширяется ссылкой на выбранный VibeType (может быть пустой). Поля vibe_category/vibe_month заменяются FK на VibeType; при миграции существующие значения конвертируются в записи VibeType по совпадению имени.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Задание с тремя пунктами считается выполненным только после того, как все три пункта закрыты — в 100% тестовых сценариев.
- **SC-002**: Награда-подарок применяется к корзине автоматически, без дополнительных действий пользователя, и снижает стоимость позиции до нуля в 100% случаев, когда подходящий товар есть в корзине.
- **SC-003**: Пользователь может выбрать, сменить или сбросить вайб за одно действие (один API-вызов).
- **SC-004**: После удаления типа вайба кассовым аппаратом ни один пользователь не сохраняет ссылку на этот вайб — проверяется немедленно после операции удаления.
- **SC-005**: При генерации задания для пользователя с вайбом сгенерированное задание относится к одной из категорий вайба в ≥90% случаев на синтетических профилях.
- **SC-006**: Запрос к CRUD-эндпоинтам вайба без валидного API-ключа отклоняется в 100% случаев.

## Assumptions

- Кассовый аппарат аутентифицируется через статический API-ключ (уже реализовано в проекте); отдельный JWT для POS не требуется.
- Один пользователь может выбрать не более одного вайба одновременно.
- Награда-подарок применяется автоматически системой при расчёте; пользователь не выбирает вручную, к какой позиции её применить.
- При category-уровне подарка скидка идёт на самый дешёвый подходящий товар в корзине.
- Если у пользователя несколько наград-подарков и все применимы, применяются все.
- Срок действия награды-подарка совпадает со сроком действия соответствующего задания (дедлайн задания).
- Пункты составного задания связаны логикой AND (все должны быть выполнены); логика OR в скоуп не входит.
- Купленный товар засчитывается в прогресс всех применимых пунктов задания параллельно (SKU-пункт и категориальный пункт не конкурируют).
- Существующая схема заданий мигрируется без потери данных: старые задания преобразуются в задания с одним пунктом.
- Поля vibe_category/vibe_month на пользователях заменяются FK на VibeType; при миграции создаются VibeType-записи из VIBE_CATEGORIES и пользователи привязываются по совпадению имени.
- Вайб задаёт предпочтительное направление рекомендаций, не жёсткое ограничение; LLM может отступить от него при явном противоречии с историей пользователя.
