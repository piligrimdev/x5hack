# Feature Specification: Docker Compose Setup

**Feature Branch**: `002-docker-compose-setup`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Необходимо добавить контейнеризацию в docker - веб сервер должен запускаться внутри docker compose, быть доступен к запросам извне, перед запуском сервера должны быть запущены проверки наличия схемы бд, применение необходимых миграций. Также документация /docs должна быть доступна через scalars c помощью scalar-fastapi"

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Запуск сервиса одной командой (Priority: P1)

Разработчик поднимает весь стек (бэкенд + БД) одной командой без ручной настройки БД. После запуска сервис доступен для HTTP-запросов с хост-машины.

**Why this priority**: Это фундаментальная задача — без неё все остальные сценарии недостижимы. Воспроизводимый запуск критичен для командной разработки и демо.

**Independent Test**: Выполнить `docker compose up` в корне проекта → дождаться статуса healthy → отправить `GET /health` с хост-машины → получить `{"status":"ok"}`.

**Acceptance Scenarios**:

1. **Given** только установлен Docker, **When** запускается `docker compose up`, **Then** через ≤60 секунд сервис отвечает на `GET /health` с HTTP 200.
2. **Given** сервис запущен, **When** отправляется запрос с хост-машины на опубликованный порт, **Then** запрос достигает бэкенда и возвращает ответ.
3. **Given** стек запущен, **When** выполняется `docker compose down`, **Then** все контейнеры останавливаются корректно без потери данных БД (volume сохраняется).

---

### User Story 2 — Автоматическая подготовка базы данных (Priority: P2)

Перед стартом веб-сервера автоматически проверяется наличие схемы БД и применяются все ожидающие миграции. Разработчику не нужно вручную запускать миграции.

**Why this priority**: Сервис без подготовленной схемы будет падать при первом запросе к БД. Автоматизация устраняет класс ошибок при деплое и делает стартап идемпотентным.

**Independent Test**: Запустить `docker compose up` на чистой БД → проверить логи на наличие события «миграции применены» → убедиться, что таблица версий миграций существует в БД.

**Acceptance Scenarios**:

1. **Given** БД пустая (первый запуск), **When** запускается `docker compose up`, **Then** миграции применяются автоматически до старта веб-сервера.
2. **Given** миграции уже применены, **When** перезапускается `docker compose up`, **Then** повторное применение пропускается (идемпотентность), сервис стартует без ошибок.
3. **Given** БД недоступна при старте, **When** запускается `docker compose up`, **Then** Compose удерживает старт веб-сервера до прохождения healthcheck БД; как только БД готова — веб-сервер запускается автоматически.
4. **Given** миграция содержит ошибку, **When** запускается `docker compose up`, **Then** ошибка фиксируется в логах и веб-сервер стартует (non-blocking migration failure).

---

### User Story 3 — Интерактивная документация API (Priority: P3)

Разработчик или тестировщик открывает `/docs` в браузере и видит интерактивную документацию всех API-эндпоинтов, оформленную через Scalar. Документация позволяет отправлять тестовые запросы прямо из браузера.

**Why this priority**: Документация ускоряет разработку фронтенда и мобильного приложения, не требуя отдельных инструментов. Scalar предоставляет лучший UX, чем стандартный Swagger UI.

**Independent Test**: Открыть `http://localhost:<port>/docs` в браузере → страница отображает список эндпоинтов → выполнить тестовый запрос `GET /health` через UI → получить `{"status":"ok"}`.

**Acceptance Scenarios**:

1. **Given** сервис запущен, **When** открывается `/docs` в браузере, **Then** страница загружается и отображает документацию API в интерфейсе Scalar.
2. **Given** страница `/docs` открыта, **When** пользователь нажимает «Try it» для эндпоинта `/health`, **Then** запрос выполняется и отображается ответ сервера.
3. **Given** добавлен новый эндпоинт в сервис, **When** открывается `/docs`, **Then** новый эндпоинт автоматически появляется в документации.

---

### Edge Cases

- Что происходит, если порт уже занят на хост-машине при запуске compose?
- Как сервис ведёт себя при потере соединения с БД после успешного старта?
- Что происходит при `docker compose up` без предварительного `docker compose build`?
- Работает ли документация `/docs` при перезапуске только веб-контейнера без БД?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система ДОЛЖНА предоставлять конфигурацию для запуска всего стека (веб-сервер + БД) единственной командой из корня репозитория.
- **FR-002**: Веб-сервер ДОЛЖЕН быть доступен для HTTP-запросов с хост-машины через опубликованный порт.
- **FR-003**: БД ДОЛЖНА сохранять данные между перезапусками контейнеров (persistent storage).
- **FR-004**: Перед стартом веб-сервера ДОЛЖНА автоматически выполняться проверка готовности БД.
- **FR-005**: Перед стартом веб-сервера ДОЛЖНЫ автоматически применяться все ожидающие миграции схемы.
- **FR-006**: Применение миграций ДОЛЖНО быть идемпотентным — повторный запуск не должен приводить к ошибкам.
- **FR-007**: Веб-сервер ДОЛЖЕН стартовать только после того, как БД пройдёт healthcheck (`pg_isready`); ожидание обеспечивается через `depends_on: condition: service_healthy` в Compose-конфигурации.
- **FR-008**: В случае ошибки миграции ошибка ДОЛЖНА быть отражена в логах; веб-сервер ДОЛЖЕН стартовать несмотря на ошибку (non-blocking).
- **FR-009**: Сервис ДОЛЖЕН предоставлять эндпоинт `/docs` с интерактивной документацией API, доступной в браузере.
- **FR-010**: Документация ДОЛЖНА автоматически отражать все зарегистрированные эндпоинты без ручного обновления.
- **FR-011**: Конфигурация окружения (порты, учётные данные БД) ДОЛЖНА задаваться через переменные окружения, а не хардкодиться.

### Key Entities

- **Стек сервисов**: набор взаимосвязанных контейнеров (веб-сервер, БД), управляемых как единое целое.
- **Persistent Volume**: хранилище данных БД, переживающее перезапуск контейнеров.
- **Migration Entrypoint**: процедура инициализации, выполняемая до запуска основного процесса сервера.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Весь стек поднимается с нуля за ≤90 секунд на стандартном разработческом ноутбуке.
- **SC-002**: После запуска `GET /health` возвращает HTTP 200 менее чем за 500 мс.
- **SC-003**: При чистом запуске миграции применяются автоматически — разработчику не нужно выполнять ни одной ручной команды.
- **SC-004**: Перезапуск стека после первоначального запуска занимает ≤30 секунд (без повторного применения миграций).
- **SC-005**: Страница документации `/docs` загружается в браузере менее чем за 3 секунды.
- **SC-006**: Тестовый запрос через UI документации выполняется успешно и отображает корректный ответ.

## Assumptions

- Целевая среда выполнения — Docker Desktop на macOS/Linux разработческих машинах и Linux-серверах.
- БД — PostgreSQL (согласно конституции проекта); контейнер БД входит в состав compose-стека.
- Порт публикации сервиса — настраивается через переменную окружения; по умолчанию 8000.
- Данные БД сохраняются в именованном Docker volume (не bind mount) для переносимости.
- Переменные окружения для compose задаются через `.env`-файл в корне проекта.
- Готовность БД проверяется через нативный Docker Compose механизм: `depends_on: db: condition: service_healthy` + `pg_isready`-based healthcheck на postgres-контейнере. Retry-логика в entrypoint или Python-коде не требуется.
- Scalar используется как замена стандартного Swagger UI для `/docs` эндпоинта.
- Production-деплой (Kubernetes, облачные провайдеры) вне скоупа данной фичи.
- `docker-compose.yml` располагается в корне репозитория (`/docker-compose.yml`); `Dockerfile` — в `web/Dockerfile`. Команда запуска стека выполняется из корня репозитория.

## Clarifications

### Session 2026-09-03

- Q: Где должны находиться файлы docker-compose.yml и Dockerfile в репозитории? → A: `docker-compose.yml` в корне `/`, `Dockerfile` в `web/`
- Q: Как должны выполняться миграции — отдельный init-контейнер или entrypoint-скрипт в веб-контейнере? → A: entrypoint-скрипт (non-blocking: ошибка логируется, сервер стартует)
- Q: Как обеспечивается готовность БД перед запуском миграций — healthcheck или retry-скрипт? → A: `depends_on: condition: service_healthy` + `pg_isready` healthcheck
