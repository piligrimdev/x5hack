## User Scenarios & Testing *(mandatory)*

### User Story 1 — Посмотреть сектора колеса и баланс купонов (Priority: P1)

Авторизованный пользователь открывает колесо фортуны в мобильном приложении. Приложение запрашивает у сервера персональный список возможных призов (сектора колеса) и текущий баланс купонов. Каждый сектор содержит название приза, тип (кешбэк или подарок), понятное описание выгоды и вероятность выигрыша. Сумма вероятностей всех секторов равна 100%. Пустых секторов нет: любой исход — это приз.

На текущем этапе список призов одинаков для всех пользователей (фиксированный каталог). Контракт ответа уже персональный: в будущем тот же запрос будет возвращать список, собранный ИИ под конкретного пользователя, без смены сценария на стороне приложения.

**Why this priority**: Без секторов и баланса приложение не может нарисовать колесо и объяснить, за что списывается купон. Это вход в механику.

**Independent Test**: Авторизованный пользователь с ненулевым или нулевым балансом запрашивает состояние колеса и получает непустой список секторов с вероятностями (сумма = 100%) плюс текущее число купонов.

**Acceptance Scenarios**:

1. **Given** авторизованный пользователь, **When** приложение запрашивает состояние колеса, **Then** ответ содержит список секторов (не меньше двух), у каждого — название, тип приза (кешбэк или подарок), описание и вероятность; сумма вероятностей равна 100%.
2. **Given** два разных пользователя в одну и ту же календарную неделю, **When** оба запрашивают состояние колеса, **Then** на текущем этапе списки секторов совпадают (фиксированный каталог); контракт ответа при этом привязан к пользователю, чтобы позже список мог отличаться.
3. **Given** пользователь без единого купона, **When** он открывает колесо, **Then** сектора всё равно возвращаются, баланс купонов равен 0, кручение недоступно.
4. **Given** неавторизованный запрос, **When** клиент просит состояние колеса, **Then** запрос отклоняется как неавторизованный.

### User Story 2 — Крутить колесо и гарантированно получить приз (Priority: P1)

У пользователя есть хотя бы один купон. Он нажимает «крутить» в мобильном приложении. Приложение отправляет на сервер только факт запроса кручения — не выбранный сектор и не желаемый приз. Сервер атомарно списывает один купон, выбирает приз по заявленным вероятностям и сразу выдаёт его пользователю. В ответе приложение получает выигранный приз и новый баланс купонов, чтобы докрутить анимацию до нужного сектора.

Каждый успешный спин заканчивается призом: кешбэк начисляется на счёт баллов сразу; подарок появляется в списке активных наград и применяется при следующей покупке так же, как подарок за задание «купи 5 шоколадок — получи 1 бесплатно» (скидка на уже лежащий в корзине подходящий товар до нулевой цены).

**Why this priority**: Это ядро механики. Пока спин не списывает купон и не выдаёт приз на сервере, колесо — декорация, а клиент мог бы подделать результат.

**Independent Test**: Выдать пользователю 1 купон, запросить кручение, убедиться: баланс стал 0, в истории спинов есть запись, приз выдан (баллы выросли либо появилась активная награда-подарок). Повторный спин без купонов отклоняется.

**Acceptance Scenarios**:

1. **Given** пользователь с балансом 3 купона, **When** приложение отправляет запрос кручения, **Then** баланс становится 2, в ответе есть выигранный приз из текущего списка секторов этого пользователя, и приз уже начислен (кешбэк на счёте баллов или активный подарок).
2. **Given** пользователь с балансом 0 купонов, **When** приложение отправляет запрос кручения, **Then** запрос отклоняется, баланс не меняется, приз не выдаётся.
3. **Given** успешный спин с призом-кешбэком на сумму X рублей, **When** операция завершается, **Then** на счёт баллов пользователя начислено X баллов по тем же правилам, что и награда-кешбэк за выполненное задание; в истории баллов появляется отдельная операция начисления, связанная со спином.
4. **Given** успешный спин с призом-подарком «1 единица товара бесплатно», **When** пользователь затем кладёт подходящий товар в корзину и считает покупку, **Then** цена одной единицы этого товара обнуляется так же, как для подарка за выполненное задание.
5. **Given** два одновременных запроса кручения при балансе 1 купон, **When** сервер обрабатывает оба, **Then** успешен ровно один спин; второй отклоняется из-за нехватки купонов; баланс не уходит ниже нуля.
6. **Given** клиент передал в запросе кручения желаемый сектор или идентификатор приза, **When** сервер обрабатывает запрос, **Then** выбор приза игнорирует пожелание клиента и выполняется только на сервере по вероятностям текущего списка.

### User Story 3 — Еженедельные купоны из настройки окружения (Priority: P1)

Каждую календарную неделю система выдаёт каждому пользователю с картой лояльности N купонов. Число N задаётся настройкой окружения и может быть изменено без переписывания правил механики. Выдача идемпотентна: повторное обращение в ту же неделю не начисляет купоны снова. Пропущенные недели не доначисляются пакетом — пользователь получает купоны только за текущую неделю.

**Why this priority**: Без регулярного притока купонов колесо недоступно после первых спинов; настройка N нужна, чтобы калибровать экономику демо.

**Independent Test**: Установить N = 3. Новый пользователь в начале недели имеет 0 купонов. После первого обращения к колесу или явной проверки начислений баланс становится 3. Повторное обращение в ту же неделю оставляет баланс 3 (если спинов не было).

**Acceptance Scenarios**:

1. **Given** настройка N = 3 и пользователь, который ещё не получал купоны на этой календарной неделе, **When** он впервые в этой неделе открывает колесо или его баланс пересчитывается, **Then** ему начисляется ровно 3 купона, в истории купонов появляется запись «еженедельное начисление».
2. **Given** пользователь уже получил еженедельные купоны на этой неделе, **When** он повторно открывает колесо, **Then** повторного начисления нет.
3. **Given** пользователь пропустил одну или несколько прошлых недель, **When** наступает новая неделя и срабатывает выдача, **Then** начисляется только пакет текущей недели (N купонов), долг за пропущенные недели не выплачивается.
4. **Given** настройка N изменена с 3 на 5, **When** начинается новая календарная неделя, **Then** пользователи, ещё не получившие пакет этой недели, получают 5 купонов; уже выданные пакеты прошлых недель не пересчитываются.
5. **Given** настройка N = 0, **When** наступает новая неделя, **Then** еженедельное начисление не увеличивает баланс (пакет пустой); купоны за задания по-прежнему начисляются.

### User Story 4 — Купоны за выполнение задания (Priority: P2)

Пользователь закрывает персональное задание. Помимо основной награды задания (кешбэк или подарок) система начисляет ему фиксированное число купонов за факт выполнения. Начисление атомарно со сменой статуса задания на «выполнено» и не дублируется при повторной обработке того же задания.

**Why this priority**: Задания — основной контур продукта; купон за выполнение замыкает «сделал полезное действие → получил шанс на колесе». Без этого колесо живёт только на еженедельной порции.

**Independent Test**: Выполнить задание пользователя с нулевым балансом купонов (еженедельный пакет уже получен и потрачен). После закрытия задания баланс купонов увеличивается на 1, основная награда задания тоже выдана.

**Acceptance Scenarios**:

1. **Given** открытое задание пользователя, **When** задание переходит в статус «выполнено», **Then** пользователю начисляется 1 купон, в истории купонов появляется запись «за задание», связанная с этим заданием.
2. **Given** задание уже закрыто и купон начислен, **When** обработчик повторно обрабатывает то же задание, **Then** второй купон не начисляется.
3. **Given** одно выполнение задания, **When** операция завершается, **Then** пользователь получает и основную награду задания (кешбэк или подарок), и купон; одно не подменяет другое.
4. **Given** истекшее (невыполненное) задание, **When** оно заменяется новым, **Then** купон за истечение не начисляется.

---

### User Story 5 — История кручений и понятный итог приза (Priority: P2)

Пользователь хочет понять, что уже выиграл и сколько купонов потратил. Он видит список последних кручений: дата, списанный купон, тип и описание приза, статус выдачи. Для кешбэка видна сумма в рублях/баллах; для подарка — какой товар или категория станет бесплатным и что подарок ещё не использован либо уже применён в покупке.

**Why this priority**: Доверие к случайной выдаче на сервере. Без истории пользователь не отличит «мне не повезло» от «приз потерялся».

**Independent Test**: Совершить два спина (кешбэк и подарок). Запрос истории возвращает обе записи в обратном хронологическом порядке с заполненным описанием приза.

**Acceptance Scenarios**:

1. **Given** пользователь с двумя успешными спинами, **When** он запрашивает историю кручений, **Then** видит обе записи от новых к старым, каждая с датой, типом приза и понятным описанием.
2. **Given** пользователь ни разу не крутил колесо, **When** он запрашивает историю, **Then** получает пустой список без ошибки.
3. **Given** неавторизованный запрос истории, **When** он обрабатывается, **Then** запрос отклоняется как неавторизованный.

---

### Edge Cases

- Пользователь запрашивает кручение в момент, когда еженедельный пакет ещё не начислен, но календарная неделя уже новая — система сначала начисляет пакет текущей недели, затем проверяет баланс и выполняет спин в одной согласованной операции (либо пакет начисляется при чтении баланса до спина; спин не должен «не увидеть» только что положенные купоны).
- Два параллельных спина при одном купоне — успешен только один; баланс не отрицательный.
- Повтор отправки того же кручения из-за обрыва сети — без явного ключа идемпотентности повтор считается новым спином, если первый уже списал купон. Приложение не должно автоматически повторять кручение; при сомнении оно перечитывает историю и баланс.
- Выигран подарок, а подходящего товара нет в каталоге — спин всё равно фиксируется, подарок остаётся в списке наград, но не применяется к корзине, пока товар недоступен (как существующая награда-подарок).
- Выигран кешбэк при отсутствии счёта баллов — счёт создаётся лениво, баллы начисляются в той же операции, что и спин.
- N в настройке окружения задано отрицательным или нечисловым — система не стартует выдачу с некорректным значением; допустимы только целые N ≥ 0.
- Пользователь без карты лояльности пытается крутить колесо — запрос отклоняется: колесо и купоны доступны только держателю карты лояльности.
- Список секторов на текущем этапе фиксированный, но в будущем станет персональным: уже выданный (но ещё не применённый) подарок и уже начисленный кешбэк не пересчитываются при смене каталога.
- Одновременно закрывается задание (начисление купона) и выполняется спин — операции согласованы: баланс не уходит ниже нуля и не теряет начисление.

## Requirements *(mandatory)*

### Functional Requirements

#### Сектора колеса и источник истины случайности

- **FR-001**: Система ДОЛЖНА отдавать авторизованному пользователю с картой лояльности актуальный список возможных призов (секторов) вместе с вероятностью каждого сектора.
- **FR-002**: Сумма вероятностей секторов ДОЛЖНА быть равна 100%. Пустой исход (сектор «ничего») ЗАПРЕЩЁН: каждый успешный спин выдаёт ровно один приз.
- **FR-003**: Контракт списка секторов ДОЛЖЕН быть персональным (привязан к пользователю). На текущем этапе содержимое списка одинаково для всех (фиксированный каталог). Замена источника списка на ИИ-генерацию НЕ ДОЛЖНА требовать смены сценария «получить сектора → крутить».
- **FR-004**: Выбор выигравшего сектора ДОЛЖЕН выполняться только на сервере по вероятностям текущего списка пользователя. Мобильное приложение передаёт намерение крутить, но НЕ выбирает приз.
- **FR-005**: Ответ на кручение ДОЛЖЕН содержать выигранный приз (тип, описание, величина кешбэка или параметры подарка) и баланс купонов после списания, чтобы приложение отобразило исход.

#### Купоны

- **FR-006**: Одно кручение ДОЛЖНО стоить ровно 1 купон. При балансе 0 кручение ДОЛЖНО быть отклонено без выдачи приза.
- **FR-007**: Баланс купонов пользователя НИКОГДА не должен становиться отрицательным.
- **FR-008**: Каждую календарную неделю (понедельник 00:00, часовой пояс продукта) система ДОЛЖНА начислять пользователю N купонов, где N задаётся настройкой окружения. Выдача за конкретную неделю идемпотентна.
- **FR-009**: Пропущенные недели НЕ ДОЛЖНЫ доначисляться задним числом: выдаётся только пакет текущей недели.
- **FR-010**: При переходе задания в статус «выполнено» система ДОЛЖНА начислить пользователю 1 купон в дополнение к основной награде задания. Начисление идемпотентно по заданию.
- **FR-011**: Истёкшее невыполненное задание НЕ ДОЛЖНО начислять купон.
- **FR-012**: Система ДОЛЖНА хранить историю операций с купонами (еженедельное начисление, начисление за задание, списание за спин) с датой, типом, количеством и связью с заданием или спином.
- **FR-013**: Еженедельное начисление ДОЛЖНО происходить лениво при обращении пользователя к колесу или балансу купонов, чтобы не требовать отдельного ручного запуска для демо.

#### Призы

- **FR-014**: Приз ДОЛЖЕН быть одного из двух типов: кешбэк (начисление баллов) или подарок (бесплатная единица подходящего товара).
- **FR-015**: Приз-кешбэк ДОЛЖЕН начисляться на существующий счёт баллов пользователя по тем же правилам, что награда-кешбэк за задание (сумма в рублях → баллы as-is), атомарно со списанием купона и записью спина.
- **FR-016**: Приз-подарок ДОЛЖЕН создавать активную награду того же вида, что подарок за задание «купи 5 шоколадок — получи 1 бесплатно»: скидка на уже добавленный в корзину подходящий товар до нулевой цены, с привязкой к товару или категории и количеством бесплатных единиц.
- **FR-017**: Применение подарка с колеса при расчёте корзины и фиксации чека ДОЛЖНО повторно использовать уже заданные правила подарка (самый дешёвый подходящий товар при категории; одноразовость; срок действия).
- **FR-018**: Списание купона, выбор приза и выдача приза ДОЛЖНЫ быть одной атомарной операцией: либо купон списан и приз выдан, либо ничего не изменилось.
- **FR-019**: Параллельные кручения одного пользователя ДОЛЖНЫ быть согласованы так, чтобы нельзя было списать больше купонов, чем есть на балансе.

#### Доступ и история

- **FR-020**: Просмотр секторов, баланса, истории и кручение ДОЛЖНЫ требовать авторизации пользователя с картой лояльности. Иначе — отказ.
- **FR-021**: Система ДОЛЖНА отдавать историю кручений пользователя (дата, приз, списанный купон) в обратном хронологическом порядке.
- **FR-022**: Фиксированный каталог секторов текущего этапа ДОЛЖЕН включать оба типа призов и ненулевые вероятности; конкретный состав зафиксирован в допущениях и может быть заменён ИИ-списком без смены требований FR-001–FR-005.

### Key Entities

- **CouponAccount (счёт купонов)**: Баланс купонов держателя карты лояльности. Баланс — целое число ≥ 0. Один счёт на пользователя/карту.
- **CouponTransaction (операция с купонами)**: Начисление или списание. Типы: еженедельный пакет, награда за выполненное задание, списание за спин. Связь с неделей, заданием или спином.
- **WeeklyCouponGrant (выдача недели)**: Факт, что пользователь уже получил пакет N купонов за конкретную календарную неделю. Обеспечивает идемпотентность FR-008.
- **WheelSector (сектор колеса)**: Возможный приз в списке пользователя: тип (кешбэк / подарок), величина или параметры подарка, вероятность, пользовательское название. Сейчас берётся из фиксированного каталога; позже — из ИИ-генерации.
- **WheelSpin (кручение)**: Факт спина: пользователь, списанный купон, выбранный сервером сектор, время, статус выдачи приза. Источник истины для истории.
- **Reward (награда-подарок)**: Существующая сущность. Подарок с колеса создаёт такую же активную награду, как подарок за задание.
- **PointsAccount / PointsTransaction**: Существующие сущности баллов. Кешбэк с колеса создаёт начисление, связанное со спином, а не с заданием.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% успешных кручений заканчиваются выдачей ровно одного приза (кешбэк или подарок); доля «спин без приза» равна 0.
- **SC-002**: При балансе 0 кручение отклоняется в 100% попыток, баланс не меняется.
- **SC-003**: На дистанции ≥ 200 спинов по фиксированному каталогу наблюдаемые доли призов отклоняются от заявленных вероятностей не более чем на 10 процентных пунктов для каждого сектора (проверка честности серверного выбора).
- **SC-004**: Пользователь, ещё не получавший пакет текущей недели, после первого обращения к колесу имеет на балансе ровно N купонов (если спина ещё не было); повторное обращение в ту же неделю не увеличивает баланс.
- **SC-005**: 100% выполненных заданий начисляют ровно 1 купон; 100 повторных обработок одного задания создают ровно 1 начисление купона.
- **SC-006**: Пользователь получает результат кручения (приз и новый баланс) менее чем за 3 секунды в 95% запросов.
- **SC-007**: Список секторов и баланс доступны приложению за одно обращение; пользователь понимает, что именно можно выиграть и сколько попыток осталось, без дополнительных шагов.
- **SC-008**: Подарок, выигранный на колесе, снижает цену подходящего товара в корзине до нуля в 100% случаев, когда товар уже в корзине — так же, как подарок за задание.
- **SC-009**: При двух одновременных кручениях и одном купоне итоговый баланс равен 0, выдан ровно один приз.

## Assumptions

- Скоуп этой спецификации — серверные операции и контракт, которым пользуется мобильное приложение. Анимация колеса, отрисовка секторов и жесты — ответственность мобильного клиента: он крутит картинку к сектору, который вернул сервер.
- Генерация секторов ИИ — следующий этап. Сейчас каталог фиксированный и одинаковый для всех. Контракт «список секторов пользователя» уже персональный, чтобы не ломать клиент при подключении ИИ.
- Фиксированный каталог текущего этапа (сумма вероятностей = 100%):

  | Сектор                         | Тип     | Величина / содержание                         | Вероятность |
  | ------------------------------ | ------- | --------------------------------------------- | ----------- |
  | Небольшой кешбэк               | кешбэк  | 10 ₽ на счёт баллов                           | 40%         |
  | Средний кешбэк                 | кешбэк  | 30 ₽ на счёт баллов                           | 30%         |
  | Подарок: 1 шоколадка бесплатно | подарок | 1 бесплатная единица товара категории «сладкое» / шоколад, как в задании «5+1» | 20%         |
  | Крупный кешбэк                 | кешбэк  | 100 ₽ на счёт баллов                          | 10%         |

- Одно кручение = 1 купон. Другие цены спина не поддерживаются.
- N еженедельных купонов задаётся настройкой окружения. Значение по умолчанию: **3**. Допустимы целые N ≥ 0.
- Календарная неделя начинается в понедельник 00:00 в часовом поясе продукта (по умолчанию Europe/Moscow).
- Пропущенные недели не компенсируются. Купоны не сгорают в конце недели: неиспользованный остаток накапливается.
- За выполненное задание начисляется **1** купон сверх основной награды задания. Истечение задания купонов не даёт.
- Кешбэк с колеса использует уже существующие баллы и курс (спека 007): начисление as-is (`баллы = целая часть суммы в рублях`).
- Подарок с колеса использует уже существующую награду-подарок (спека 008): скидка на товар, который пользователь сам положил в корзину; при категории — самый дешёвый подходящий; одноразовый.
- Срок действия подарка с колеса — 7 дней с момента выигрыша (аналог дедлайна задания), чтобы подарок не висел бессрочно.
- Колесо доступно только авторизованному держателю карты лояльности — как баллы.
- Еженедельная выдача ленивая: при первом запросе состояния колеса или баланса в новой неделе. Отдельный ночной прогон не обязателен для демо.
- Повтор кручения при обрыве сети без ключа идемпотентности считается новым спином, если первый уже прошёл. Клиент не ретраит кручение автоматически.
- Возврат купона при отмене чека, передача купонов между пользователями, покупка купонов и ручная настройка каталога оператором — вне скоупа.
- Принцип II конституции в общем виде запрещает новые игровые механики сверх аватара, челленджа и рейтинга. Эта механика добавляется явно по запросу команды для демо хакатона: колесо тратит купоны, полученные в том числе за челленджи, а выигрыш выражен в рублях экономии (кешбэк или бесплатный товар). Перед показом жюри как «готово к пилоту» нужна явная команда на поправку конституции и расчёт юнит-экономики (принцип IV): ожидаемая стоимость приза при заданных вероятностях и N ≤ ожидаемый прирост маржи.
