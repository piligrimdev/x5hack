# Feature Specification: Dual-Consumer Authorization

**Feature Branch**: `003-auth`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "Добавим фичу авторизации. Апи будет использоваться двумя потребителями - пользователи мобильного приложения (клиенты) и кассовые аппараты. Авторизация для пользователей — JWT токены на устройстве. Регистрация по номеру телефона (2FA/пароли — в беклог). Номер телефона уникален, нормализуется. Дубликат — 409. Кассы — статичные токены (ротация — беклог)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Регистрация пользователя по телефону (Priority: P1)

Новый пользователь мобильного приложения вводит номер телефона. Система нормализует номер, проверяет уникальность и выдаёт пару JWT-токенов (access + refresh). Пользователь сразу попадает в приложение — без дополнительных шагов.

**Why this priority**: Без регистрации невозможно использовать лояльность. Это единственная точка входа в продукт.

**Independent Test**: Отправить запрос с корректным номером телефона → получить пару access + refresh токенов → убедиться, что access token позволяет делать авторизованные запросы.

**Acceptance Scenarios**:

1. **Given** новый пользователь с валидным номером телефона, **When** отправляет запрос на регистрацию, **Then** система сохраняет пользователя и возвращает пару `access_token` + `refresh_token` в теле ответа.
2. **Given** пользователь с уже зарегистрированным номером телефона, **When** отправляет запрос на регистрацию, **Then** система возвращает 409 и сообщение о конфликте.
3. **Given** номер телефона в нестандартном формате (например, `8 (495) 123-45-67`), **When** пользователь регистрируется, **Then** система нормализует номер и сохраняет в каноническом формате перед проверкой уникальности.
4. **Given** некорректный номер телефона (слишком короткий, буквы), **When** пользователь отправляет запрос, **Then** система возвращает 422 с описанием ошибки.

---

### User Story 2 — Повторный вход зарегистрированного пользователя (Priority: P2)

Пользователь с существующей учётной записью входит по номеру телефона и получает новые JWT-токены.

**Why this priority**: Пользователи теряют устройства, переустанавливают приложение. Нужен механизм повторного входа.

**Independent Test**: Зарегистрироваться → выйти → войти с тем же номером → получить рабочий токен.

**Acceptance Scenarios**:

1. **Given** зарегистрированный пользователь с валидным номером, **When** отправляет запрос на вход, **Then** система возвращает пару `access_token` + `refresh_token`.
2. **Given** номер, не зарегистрированный в системе, **When** отправляет запрос на вход, **Then** система возвращает 404.
3. **Given** нормализованный номер телефона, **When** пользователь вводит его в любом допустимом формате, **Then** система распознаёт как существующий аккаунт.

---

### User Story 3 — Аутентификация кассового аппарата (Priority: P2)

Кассовый аппарат (PoC: симулируется) передаёт статичный токен в заголовке запроса и получает доступ к API создания покупок и запроса карт лояльности.

**Why this priority**: Без авторизации касс невозможно имитировать оффлайн-покупки и привязку карты лояльности — ключевой сценарий демо.

**Independent Test**: Отправить запрос с валидным статичным токеном кассы → получить 200 на защищённом кассовом эндпоинте.

**Acceptance Scenarios**:

1. **Given** запрос с валидным статичным токеном кассы, **When** касса обращается к кассовому API, **Then** запрос проходит авторизацию.
2. **Given** запрос без токена или с некорректным токеном, **When** касса обращается к кассовому API, **Then** система возвращает 401.
3. **Given** корректный токен пользователя (JWT), **When** используется для запроса к кассовому API, **Then** система возвращает 403 (неправильный тип потребителя).

---

### User Story 4 — Защита пользовательских эндпоинтов (Priority: P1)

Авторизованные пользовательские запросы (профиль, история покупок, челлендж) требуют валидный JWT. Без токена — 401.

**Why this priority**: Базовая безопасность API — без неё утечка данных между профилями.

**Independent Test**: Обратиться к защищённому эндпоинту без токена → получить 401. Обратиться с токеном → получить данные.

**Acceptance Scenarios**:

1. **Given** запрос без заголовка Authorization, **When** обращение к защищённому эндпоинту, **Then** система возвращает 401.
2. **Given** просроченный или повреждённый JWT, **When** обращение к защищённому эндпоинту, **Then** система возвращает 401.
3. **Given** валидный JWT зарегистрированного пользователя, **When** обращение к своим данным, **Then** система возвращает данные только этого пользователя.

---

### User Story 5 — Обновление токенов через refresh (Priority: P2)

Мобильный клиент, у которого истёк access token, отправляет refresh token на `/refresh` и получает новую пару access + refresh токенов без повторного ввода номера телефона.

**Why this priority**: Позволяет пользователю оставаться авторизованным после истечения 7-дневного access token, не требуя повторного входа.

**Independent Test**: Получить пару токенов при входе → отправить refresh token на `/refresh` → получить новую пару → убедиться, что новый access token работает на защищённом эндпоинте.

**Acceptance Scenarios**:

1. **Given** действующий refresh token, **When** клиент отправляет `POST /refresh` с токеном в теле, **Then** система возвращает новую пару `access_token` + `refresh_token`.
2. **Given** просроченный refresh token, **When** клиент отправляет `POST /refresh`, **Then** система возвращает 401.
3. **Given** access token (вместо refresh token) в теле `/refresh`, **When** клиент отправляет запрос, **Then** система возвращает 401.

---

### Edge Cases

- Что происходит при регистрации с номером, отличающимся только форматом от уже существующего (например, `+79161234567` и `79161234567`)?
  → Система нормализует оба к одному формату и блокирует регистрацию с 409.
- Что происходит при отправке пустой строки как номера телефона?
  → 422 с описанием ошибки валидации.
- Что происходит при попытке использовать кассовый токен на пользовательском эндпоинте?
  → 403, разные типы потребителей изолированы.
- Что происходит при JWT с корректной подписью, но несуществующим user_id?
  → 401, пользователь не найден.
- Что происходит при передаче просроченного refresh token на `/refresh`?
  → 401, новая пара токенов не выдаётся.
- Что происходит при передаче access token (вместо refresh token) на `/refresh`?
  → 401, токен отклоняется (тип `typ` в payload не совпадает).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать регистрацию пользователя с номером телефона как единственным идентификатором.
- **FR-002**: Система MUST нормализовать номер телефона к формату E.164 (`+7XXXXXXXXXX` для российских номеров) перед любой проверкой или сохранением.
- **FR-003**: Система MUST обеспечивать уникальность нормализованного номера телефона; дублирующая регистрация возвращает 409.
- **FR-004**: Система MUST выдавать пару токенов (`access_token` + `refresh_token`) при успешной регистрации или входе пользователя. Access TTL — 7 дней, refresh TTL — 14 дней.
- **FR-012**: Система MUST предоставлять эндпоинт `POST /refresh`, принимающий действующий refresh token и возвращающий новую пару `access_token` + `refresh_token`.
- **FR-013**: Система MUST отклонять запрос на `/refresh` с просроченным или недействительным refresh token → 401.
- **FR-005**: Система MUST защищать пользовательские эндпоинты через проверку JWT; отсутствие или недействительный токен → 401.
- **FR-006**: Система MUST поддерживать авторизацию кассовых аппаратов через предзаданный статичный токен, передаваемый в заголовке `X-Terminal-Token`.
- **FR-007**: Система MUST изолировать зоны доступа: JWT-токены пользователей не дают доступ к кассовым эндпоинтам и наоборот; нарушение → 403.
- **FR-008**: Система MUST возвращать 422 при некорректном формате номера телефона (слишком короткий, содержит недопустимые символы).
- **FR-009**: Пользовательский эндпоинт входа (`/login`) MUST возвращать 404, если номер телефона не зарегистрирован.
- **FR-010**: Каждый зарегистрированный пользователь MUST получать уникальный идентификатор (UUID), используемый для привязки данных (покупки, челленджи).
- **FR-011**: Все ошибочные ответы API (401, 403, 404, 409, 422) MUST возвращать тело в формате `{"detail": "сообщение"}` — стандартный формат FastAPI.

### Key Entities

- **User**: зарегистрированный клиент; атрибуты — UUID, нормализованный номер телефона, дата регистрации.
- **JWT Access Token**: токен, выдаваемый пользователю при входе/регистрации/обновлении; содержит UUID пользователя и срок действия (TTL 7 дней); хранится на устройстве; используется в `Authorization: Bearer`.
- **JWT Refresh Token**: долгоживущий токен (TTL 14 дней), выдаваемый вместе с access token; используется исключительно для получения новой пары токенов через `POST /refresh`; различается от access token полем `typ` в payload.
- **Terminal Token**: статичный предзаданный токен кассового аппарата; идентифицирует кассу как авторизованного потребителя API.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Регистрация нового пользователя завершается и пара токенов (access + refresh) выдаётся в течение 2 секунд.
- **SC-002**: Попытка повторной регистрации с существующим номером (в любом формате) отклоняется с 409 в течение 1 секунды.
- **SC-003**: 100% запросов к защищённым пользовательским эндпоинтам без действительного JWT получают отказ (401).
- **SC-004**: 100% запросов к кассовым эндпоинтам с JWT пользователя (вместо токена кассы) получают 403.
- **SC-005**: Кассовый аппарат с валидным токеном может создать покупку и получить информацию о карте лояльности без дополнительных шагов.
- **SC-006**: Нормализация охватывает не менее 5 распространённых форматов российских номеров телефонов (с 8, с +7, с пробелами, с дефисами, со скобками).

## Assumptions

- Нормализация телефона: приведение к формату E.164 (`+7XXXXXXXXXX`) покрывает основные форматы российских номеров; международные номера вне скоупа PoC.
- JWT stateless: сервер не хранит токены и не поддерживает revocation в PoC.
- Статичный токен кассы задаётся через переменную окружения (конфигурацию); управление множеством токенов — backlog.
- Кассовые аппараты в PoC симулируются (нет интеграции с production-системами X5 согласно конституции проекта).
- Одна пара «телефон → UUID» на пользователя; смена номера телефона — backlog.
- Пароли и 2FA явно выведены в backlog; в PoC вход = регистрация по номеру без дополнительных шагов подтверждения.
- Access token передаётся в заголовке `Authorization: Bearer`; хранение токенов — ответственность мобильного клиента.
- Access token TTL — 7 дней; refresh token TTL — 14 дней.
- Refresh token используется только для `POST /refresh`; передавать его в `Authorization: Bearer` запрещено.

- Q: Через какой HTTP-заголовок кассовый аппарат передаёт статичный токен? → A: `X-Terminal-Token`

- Q: Нужен ли refresh token, и какой у него TTL? → A: Да; `/register` и `/login` возвращают пару access+refresh; `POST /refresh` обменивает refresh на новую пару; TTL refresh — 14 дней
