# Корзина и Аппи

Модель: `google/gemini-3.1-flash-lite` через OpenRouter. Настройки:
`BASKET_LLM_MODEL`, `OPENROUTER_API_KEY`.

После каждого входа `AppContent` запускает одну фоновую сборку недельной
корзины. Переходы между экранами не пересоздают запрос. Сохранённые товары
восстанавливаются до результата LLM, затем заменяются им; ошибка сохраняет
предыдущую корзину. После заказа корзина остаётся пустой до явного запроса
или нового входа. Параллельные изменения блокируются.

## Цены

Модель получает `price_rub` после действующих скидок и `base_price_rub` до
скидок. Используются тот же `DiscountCalculatorService`, магазин последнего
чека (либо первый доступный), карта и уровень лояльности, что при оформлении.
Персональные скидки учитываются. Карта цен рассчитывается для всего каталога
одним вызовом; текущий расчётчик применяет скидки к цене единицы независимо
от количества. Бюджет проверяется по этой же карте через Decimal. Списание
баллов в бюджет не входит. При изменении цен/скидок после подбора актуальная
сумма заново рассчитывается в preview/checkout.

## Пять функций модели

- `add_recipe_ingredients`: полный набор продуктов для блюда за один вызов,
  количество — упаковки на две порции по умолчанию. Сервер учитывает уже
  имеющиеся товары без повторного добавления, сохраняет остальные позиции.
  Недоступные ингредиенты показываются в сообщении.
- `build_budget_basket`: основной и при необходимости запасной полноценный
  вариант. Сервер выбирает ближайший к бюджету без превышения после скидок.
  Этот инструмент доступен модели только при явно указанной пользователем
  сумме или слове «бюджет». Количество товаров, число порций и исторические
  недельные траты бюджетом не считаются; оценка недельных трат скрывается от
  модели во всех обычных запросах.
  Если варианты не подходят — одна повторная попытка с исходным лимитом.
  «Ужин на 700» создаёт новую корзину, явное добавление сохраняет текущую,
  но лимит проверяется на весь итог. Ошибка не меняет корзину.
- `add_challenge_products`: модель выбирает подходящие SKU, сервер рассчитывает
  недостающее количество с учётом прогресса и пересечения заданий. Условия
  суммы чека показываются отдельно. Добавление не завершает задание.
- `replace_basket`: полная недельная корзина или конечное состояние после
  отдельной правки. Незатронутые товары сохраняются при правках.
- `explain`: уточнение или пояснение без изменения товаров.

Статистического fallback нет. Сервер проверяет SKU, дубликаты, количества
1–50 и лимит 40 позиций для полных планов. Невалидный план не применяется.

Персональный контекст: агрегаты покупок за 90 дней, частота и количество за
неделю, последние даты, обычные недельные расходы, активные задания с точными
SKU и критериями. Телефон, идентификатор пользователя и платёжные реквизиты
не передаются. История направляет недельный подбор; запрос конкретного блюда
имеет приоритет над историей и заданиями.

## Проверки

- `python3 -m poetry -C web run pytest tests/webx5/services/test_basket_budget.py tests/webx5/services/test_basket_challenge_context.py tests/webx5/services/test_basket_assistant.py tests/webx5/routes/test_basket.py tests/webx5/core/test_llm.py -q`
- `cd x5mobile && npx tsc --noEmit`
- `node x5mobile/scripts/test-basket-session.cjs`

Реальные LLM smoke-тесты выполняются на вымышленных каталогах/заданиях;
персональные данные не нужны для проверки протокола и типовых запросов.
