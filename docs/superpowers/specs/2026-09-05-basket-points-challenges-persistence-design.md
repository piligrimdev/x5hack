## Контекст

Четыре независимых доработки поверх уже работающей корзины:

1. **Курс начисления баллов не согласован со списанием.** Списание уже идёт по курсу
   `PointsSettings.rate_points_per_rub = 10` (10 баллов = 1 ₽, задано миграцией
   `g5b6c7d8e9f0`). Начисление же (`PointsService.award_for_task`) сейчас — `points =
   int(task.reward_rub)`, то есть 1 балл = 1 ₽ награды. Итог: награда за задание в 100 ₽
   даёт 100 баллов, которые при списании стоят всего 10 ₽ — десятикратная потеря
   ценности. Согласовано с пользователем: начисление должно использовать тот же курс
   (×10), с округлением до 10.
2. **Секция "Задания" на экране "Экономия" показывает моковые данные.** `savings-view.tsx`
   получает `tasks: Task[]` из `useMockData()` (`x5mobile/src/mock-data.ts`) — захардкоженный
   список, не связанный с реальными челленджами пользователя. При этом полноценный
   реальный API (`GET /challenges/current`) и хук (`useChallenges`) уже существуют и
   используются на отдельном экране `challenges-view.tsx`.
3. **Тумблер "Списать баллы" не меняет "Итого".** Сейчас — отдельная строка "Итого с
   баллами" рядом с неизменным "Итого", что визуально не читается как одна сумма к
   оплате.
4. **Корзина на неделю не персистентна и не пустая при первом заходе.** Сейчас
   `useBasket` при каждом монтировании сам вызывает `GET /basket/suggested` — корзина
   никогда не бывает пустой и полностью пересобирается при каждом переходе на экран,
   теряя любые правки через ассистента "Аппи". Нужно: при первом заходе — пустая
   корзина с кнопкой явного сбора; после сбора — состояние сохраняется на устройстве и
   переживает повторные заходы на экран.

## 1. Курс начисления баллов

`PointsService.award_for_task` (`web/src/webx5/services/points.py:44`) получает курс через
уже существующий `PointsRepository.get_rate(session) -> int` (используется в
`preview_for_calculate`, `services/points.py:150-160`, читает
`PointsSettings.rate_points_per_rub`, сейчас `10`).

Новая формула:
```python
rate = self._repo.get_rate(session)
raw = float(task.reward_rub) * rate
points = int(round(raw / 10) * 10)  # округление до 10
```
За 100 ₽ награды при курсе 10 → `round(1000/10)*10 = 1000` баллов. Дробная
`reward_rub` (например 33.33) → `round(333.3/10)*10 = 330`. Проверка `if points <= 0:
skip` остаётся без изменений — существующая идемпотентность (`insert_earn` возвращает
`None` при повторном вызове) не трогается.

`web/tests/webx5/services/test_points_award.py` — 4 существующих теста считают по
старой формуле (`reward=50 → awarded=50`) и используют голый `MagicMock()` без
`get_rate.return_value` — все нужно обновить: добавить `repo.get_rate.return_value = 10`
и пересчитать ожидаемые значения (`reward=50 → awarded=500`). `test_award_for_task_reward_rub_decimal_is_floored`
(reward=50.99 → 50) меняет смысл — новая формула не "floor", а "scale+round-to-10"
(50.99 → 510), тест нужно переименовать и пересчитать.

## 2. Реальные челленджи в корзине

`savings-view.tsx` перестаёт принимать `tasks: Task[]` — вместо этого вызывает уже
существующий `useChallenges(token)` (`x5mobile/src/hooks/useChallenges.ts`) и рендерит
`current: ChallengeItem[]`. `TaskCard` адаптируется под поля `ChallengeItem` (`title`,
`description`, `quantity_current`/`quantity_target`, `reward_rub`, `status`) вместо
`Task`-полей мока (`sub`, `progress`, `total`, `done`, `reward`). `done` выводится как
`status === 'выполнено'` (то же соглашение, что и в `challenges-view.tsx`).
`index.tsx` перестаёт передавать `tasks={data.tasks}` в `<SavingsView>`. `mock-data.ts` и
`useMockData()` не трогаются — используются в других местах (лидерборд), только
`tasks` перестаёт доходить до `SavingsView`.

## 3. "Итого" реагирует на списание баллов

`savings-view.tsx`'s totals-блок: строка "Итого" показывает
`preview.cashback.total_paid_rub` (вместо суммы по товарам), когда тумблер включён и
`cashback_rub > 0`, иначе — прежнюю сумму по товарам. Строка "Итого с баллами"
убирается, вместо неё под тумблером — строка "Баллами: −N ₽" (тот же зелёный стиль,
что у "Скидка").

## 4. Персистентная корзина на неделю

**Хранилище:** `@react-native-async-storage/async-storage` (новая зависимость, `npx expo
install @react-native-async-storage/async-storage` — резолвит версию под Expo ~57).
Один фиксированный ключ (`@x5hack/weeklyBasket`), не привязан к конкретному
пользователю — на одном устройстве корзина общая для всех аккаунтов. Осознанное
упрощение PoC (см. "Вне объёма" ниже).

**`useBasket` меняется:**
- Автозагрузка `GET /basket/suggested` при монтировании убирается.
- При монтировании — чтение из `AsyncStorage`. Если ключ есть (даже пустой массив) —
  `items` восстанавливаются, `hasCollected = true`. Если ключа нет — `items = []`,
  `hasCollected = false`. Флаг `hydrated` защищает от отображения "не собрана" на
  долю секунды до завершения асинхронного чтения.
- Новая функция `collectWeeklyBasket()`: вызывает `GET /basket/suggested`, пишет
  результат в `items`, ставит `hasCollected = true`.
- `items` (любое изменение — сбор, правки через ассистента) пишется в `AsyncStorage`
  всегда, когда `hydrated && hasCollected`.
- `checkout()` при успехе, помимо очистки `items`/`preview`/`spendPoints`, ставит
  `hasCollected = false` и удаляет ключ из `AsyncStorage` — следующий заход снова
  начинается с пустой корзины (осмысленно: "корзина на неделю" разовая, после покупки
  собирается заново).

**UI:** пустое состояние корзины (`basketItems.length === 0`, не только что
оформленный заказ) показывает кнопку "Собрать корзину на неделю" — вызывает
`collectWeeklyBasket()`. Текст над кнопкой зависит от `hasCollected`: до первого сбора
— нейтральное приглашение; после сбора с пустым результатом — прежнее "Пока нечего
предложить — мало истории покупок". Кнопки на главном экране и в таб-баре не
меняются — они как и раньше просто открывают экран "Экономия"; сама логика сбора
живёт только внутри него.
