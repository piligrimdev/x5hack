# AI-модуль: корзина на неделю + чат-ассистент добавления/удаления товаров

Date: 2026-09-04. Brainstormed interactively (`superpowers:brainstorming`).

## Проблема и место в проекте

Запрос: собрать ИИ-модуль, который (1) на основе истории покупок предлагает
пользователю "корзину на неделю" и (2) даёт возможность попросить ассистента
добавить или убрать товар из этой корзины свободным текстом.

Это почти дословно гипотеза **B5** из `CONTEXT_PACK.md` §6 ("LLM-подбор
эффективной корзины"), которая была явно помечена как *"не в фокусе первой
итерации"*. `constitution.md`, принцип II (NON-NEGOTIABLE), запрещает новые
механики поверх трёх выбранных (аватар, челлендж, рейтинг) и фиксирует скоуп
демо в 3-4 экрана.

**Решение (согласовано с пользователем):** не заводить новый экран/механику.
Ассистент встраивается **внутрь существующего экрана экономии**
(`x5mobile/src/components/screens/savings-view.tsx`) как ещё один блок —
формально это способ взаимодействия с уже одобренными механиками (экономия,
челленджи), а не четвёртая механика. `constitution.md`/`CONTEXT_PACK.md` не
меняются.

## Блокер, найденный по пути

`receipts.loyalty_card_id` — это FK на `users.id` (реальные зарегистрированные
аккаунты), но `web/scripts/seed_receipts.py` сейчас пишет туда id из
синтетических `loyalty_cards` (`uuid5` от synthetic `user_id`), не создавая
соответствующей строки в `users`. Результат: у реального залогиненного
демо-юзера сейчас нет своих чеков в БД — строить историю не из чего.

**Решение (согласовано):** починить `seed_receipts.py`, чтобы он создавал
`User`-запись с тем же id, что и синтетический `loyalty_card_id`, — тогда
демо-аккаунт может залогиниться под одним из этих id и видеть реальную
историю покупок. Детали — в implementation plan.

## Архитектура

Расширение существующего пакета `web/src/webx5` на месте, без нового
сервиса/деплой-юнита — тот же RSI-паттерн, что у `discounts`/`receipts`.

```
web/src/webx5/
  crud/basket.py                 # BasketRepository — агрегация покупок из receipts/receipt_items
  services/basket_assistant.py   # BasketService: suggest() + apply_instruction()
  routes/basket.py               # GET /basket/suggested, POST /basket/assistant
  schemas/basket.py              # BasketItem, SuggestedBasketResponse, AssistantRequest/Response
  core/llm.py                    # тонкая обёртка над OpenRouter tool-calling
```

**Без новой таблицы БД.** Договорились: взаимодействие — одно текстовое поле
+ список корзины, без истории сообщений. Ассистенту для каждого запроса
достаточно текущего снимка корзины, который присылает фронт, — персистентность
на бэке не нужна. Фронт держит список в состоянии экрана
(`useState`/локальный хук); обновление страницы теряет несохранённые правки —
приемлемый компромисс для PoC, не для продакшена (см. `BACKLOG.md`).

## API

### `GET /basket/suggested`

Авторизация: `CurrentUserUUID` (как в `routes/receipts.py`).

Детерминированно, **без LLM** — тот же принцип, что у
`build_spend_threshold_challenge`/`build_category_expansion_challenge` в
`synth/challenges.py`: там, где не нужен LLM, его не зовём.

`BasketRepository.suggest_items(session, user_id)`:
- Агрегирует `receipt_items` пользователя по `product_id` за весь наблюдаемый
  период (или ограниченное окно — например, последние 90 дней, если истории
  много) — среднее число покупок в неделю на продукт.
- Отбирает продукты с недельной каденцией (например, средняя частота
  ≥ ~0.7 раза в неделю — порог финализировать при реализации по факту
  распределения на сидированных данных, не гадать заранее).
- `quantity` = округлённое среднее количество за покупку по этому продукту.

Ответ: `SuggestedBasketResponse { items: [BasketItem { product_id, name,
quantity, price }] }`.

### `POST /basket/assistant`

Авторизация: `CurrentUserUUID`.

Тело: `AssistantRequest { items: [{product_id, quantity}], instruction: str }`
— `items` это текущее состояние корзины на фронте (то, что показывается
сейчас), не обязательно совпадает с последним `suggested`.

`BasketService.apply_instruction`:
1. Резолвит `items` в товары (join `products`) — нужны имена/цены для
   промпта и для валидации, что `product_id` вообще существуют.
2. Строит system-промпт: **весь каталог целиком** (132 SKU — умещается без
   проблем, поиска по каталогу отдельным tool-call не нужно), текущая
   корзина, инструкция пользователя.
3. Зовёт LLM (OpenRouter) с tool-calling: `add_item(product_id, quantity)`,
   `remove_item(product_id)`, `set_quantity(product_id, quantity)`.
4. **Сам детерминированно применяет** вызванные инструменты к списку —
   не доверяем модели пересчитывать/переписывать список целиком (риск, что
   она забудет позицию или ошибётся в количестве).
5. Возвращает обновлённый `items` (с резолвленными именами/ценами).

Ответ: `AssistantResponse { items: [BasketItem], applied: bool, message: str
| None }`. Если LLM не вызвалась / не смогла распарситься / не сделала ни
одного валидного tool-call — возвращаем **исходный** список без изменений,
`applied=false`, понятное `message` ("не поняла запрос, попробуй иначе") —
тот же принцип, что `generic_fallback` в `synth/challenges.py`: невалидный
результат LLM никогда не просачивается как будто он валиден.

`forbidden_categories` (алкоголь/детское питание) из `synth/challenges.py`
**сюда не переносится** — это ограничение было про то, что X5 не должен сама
проактивно рекомендовать такие категории как награду/челлендж. Здесь
пользователь explicit просит добавить конкретный товар в свою же корзину —
блокировать это не нужно.

## LLM и риски

Провайдер: OpenRouter (`OPENROUTER_API_KEY`, уже есть в `.env`), по умолчанию
`deepseek/deepseek-chat` — та же модель, что уже используется в
`synth/challenges.py`, для консистентности и стоимости.

**Открытый риск:** нет подтверждения, что `deepseek/deepseek-chat` через
OpenRouter надёжно поддерживает structured tool-calling (а не просто
следование инструкции в тексте). `synth/challenges.py` сейчас использует
только `response_format: json_object`, не настоящий function-calling API.
Проверка этого — **первая задача implementation plan** (несколько ручных
запросов с `tools=[...]` через OpenRouter, до написания `BasketService`):
если модель ненадёжна, переключиться на другую модель в OpenRouter с
подтверждённой поддержкой tool-calling — `core/llm.py` изолирует выбор
модели, остальной дизайн не меняется.

## Фронтенд

`x5mobile/src/components/screens/savings-view.tsx` — новый блок (не новый
экран): карточка "Корзина на неделю" со списком товаров (аналог `TaskCard`
по структуре) + текстовое поле снизу для инструкции ассистенту.

- При маунте экрана — `GET /basket/suggested`, результат в локальный стейт.
- Каждая отправка текста в поле — `POST /basket/assistant` с текущим
  состоянием + текстом, ответ заменяет локальный стейт целиком.
- Новый API-хелпер в `x5mobile/src/api/client.ts`: `apiGetSuggestedBasket`,
  `apiAssistBasket`.

## Тестирование

Backend (`web/tests/webx5`, зеркалит `src/`):
- `tests/webx5/crud/test_basket.py` — агрегация частоты покупок из
  сидированных receipts на известном наборе (fixture).
- `tests/webx5/services/test_basket_assistant.py` — `apply_instruction` с
  замоканным LLM-клиентом (аналог `monkeypatch.setattr("synth.challenges.
  call_openrouter", ...)` в тестах challenges): валидные tool-calls
  применяются корректно; невалидный/пустой ответ LLM → список не меняется,
  `applied=false`.
- `tests/webx5/routes/test_basket.py` — авторизация (401 без Bearer),
  happy path обоих эндпоинтов.

Ручная проверка (per project rule "для UI-изменений — запустить и проверить
в браузере/эмуляторе перед тем, как считать готовым"): реальный прогон на
сидированных данных — залогиниться демо-юзером с починенным seed, увидеть
непустую предложенную корзину, попросить ассистента добавить/убрать товар
через реальный (не замоканный) LLM-вызов хотя бы один раз.

## Явно вне скоупа

- Персистентная корзина в БД (стейт только на фронте).
- История диалога с ассистентом (каждый запрос независим).
- B6 (рекомендация магазина сети, где товар дешевле) — отдельная,
  нерассмотренная здесь гипотеза.
- Полноценный поиск по каталогу отдельным tool-call — каталог маленький,
  передаётся целиком.
